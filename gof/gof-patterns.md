# GoF Design Patterns — краткий каталог

Источник: Gamma, Helm, Johnson, Vlissides — *Design Patterns* (1994).  
Формат: **English / русский** (алиасы) → проблема → суть → в Go.

Везде речь про **типы** (в Go — `type` / интерфейс), **экземпляры** (значения этих типов) и **конструкторы** (`New…`). Слово «продукт» в учебниках = просто «созданный экземпляр»; ниже его не используем.

Go не копирует Java/C++. Часто паттерн = интерфейс + структура/функция, а не дерево наследования.

Внутри каждой группы порядок: **от простого к сложному**.

---

## Creational (порождающие)

### Singleton / Одиночка (нужен редко)
- **Проблема:** во всей программе должен жить ровно один экземпляр типа, и все берут его из одного места.
- **Суть:** конструктор прячут; первый вызов создаёт экземпляр, остальные возвращают тот же. В Go чаще передают зависимость явно, а не через глобал.
- **В Go:** `sync.Once` + переменная пакета.

### Factory Method / Фабричный метод (Virtual Constructor)
- **Проблема:** клиенту нужен экземпляр интерфейса `X`, а какой именно конкретный тип подставить — решает не клиент.
- **Суть:** вместо прямого `NewConcrete()` вызываешь метод/функцию «создай `X`»; внутри уже написано, какой тип инстанцировать. Параметр или реализация метода выбирает конкретный тип.
- **В Go:** `NewX(kind string) (X, error)` или метод интерфейса `Create() X`; часто просто `NewFoo()`.

### Prototype / Прототип (Clone)
- **Проблема:** нужен новый экземпляр «как вот этот», а точный конкретный тип снаружи знать не хочется или неудобно.
- **Суть:** у образца есть метод «сделай копию меня»; вызываешь его и получаешь новый экземпляр того же типа с теми же (или почти теми же) полями. Конструктор с нуля не зовёшь.
- **В Go:** `Clone() T` или копирование структуры / `maps.Clone` (глубокую копию пишут руками).

### Builder / Строитель (отдельно от «fluent builder»)
- **Проблема:** экземпляр сложный: много полей, собирать одним вызовом конструктора неудобно или невозможно.
- **Суть:** отдельный тип-сборщик принимает параметры по шагам (`WithX`), в конце `Build()` возвращает готовый экземпляр нужного типа. Один и тот же порядок шагов может собрать разные варианты результата.
- **В Go:** структура-builder + `Build() (T, error)`; или опции `func(*T)`.

### Abstract Factory / Абстрактная фабрика (Kit)
- **Проблема:** нужно создать сразу несколько связанных экземпляров (кнопка + меню одной темы), не привязывая клиента к конкретным типам.
- **Суть:** клиент держит интерфейс «фабрики» и зовёт её методы-конструкторы; одна реализация фабрики всегда выдаёт экземпляры из одного семейства (все «светлые» или все «тёмные»), поэтому они стыкуются друг с другом. Сменил фабрику в конструкторе/параметре клиента — сменил всё семейство разом.
- **В Go:** интерфейс `Factory` с `NewButton() Button`, `NewMenu() Menu`; две структуры-фабрики.

## Structural (структурные)

### Facade / Фасад
- **Проблема:** снаружи торчит куча типов и вызовов; клиенту нужна одна простая точка входа.
- **Суть:** один тип (или несколько функций пакета) принимает простые параметры и внутри сам создаёт/зовёт остальные экземпляры. Клиент знает только этот узкий интерфейс.
- **В Go:** пакет с `New`/`Do` и неэкспортируемыми деталями.

### Adapter / Адаптер (Wrapper)
- **Проблема:** есть экземпляр типа с «не тем» интерфейсом; нужен другой интерфейс, а чужой тип править нельзя.
- **Суть:** пишешь свой тип-обёртку: снаружи методы нужного интерфейса, внутри поле со старым экземпляром, вызовы переводишь в его методы. Клиент работает только с новым интерфейсом.
- **В Go:** структура с полем `adaptee` и методами целевого интерфейса.

### Proxy / Заместитель (Surrogate)
- **Проблема:** к экземпляру нельзя пускать напрямую: лень создавать, нужны права, сеть, кэш.
- **Суть:** подставляешь другой экземпляр с тем же интерфейсом; клиент зовёт его, а он уже решает, когда трогать настоящий объект. Снаружи тип (интерфейс) тот же.
- **В Go:** структура того же интерфейса; внутри реальный объект / RPC / `sync.Once`.

### Decorator / Декоратор (Wrapper, Skin)
- **Проблема:** к экземпляру нужно добавить поведение (лог, кэш), не меняя его тип и не плодя подтипы на каждую комбинацию.
- **Суть:** новая структура реализует тот же интерфейс, внутри держит «оригинал», в каждом методе что-то делает и делегирует ему. Снаружи тип тот же — можно вкладывать обёртки друг в друга.
- **В Go:** `loggingRoundTripper` вокруг `http.RoundTripper`.

### Bridge / Мост (Handle/Body)
- **Проблема:** две оси меняются независимо. Пример: фигуры `Circle` / `Square` и способы рисования `SVG` / `Canvas`. Без моста плодят типы на каждую пару: `CircleSVG`, `CircleCanvas`, `SquareSVG`, `SquareCanvas`… Добавил третью фигуру или третий способ — снова умножай.
- **Суть:** фигуры — одни типы; «чем рисовать» — отдельный интерфейс, экземпляр которого лежит в поле фигуры. Фигура знает *что* рисовать (свой радиус, стороны), а в поле зовёт *как* (`DrawCircle`, `DrawRect`). Новый способ рисования = новый тип под интерфейс, фигуры не трогаешь; новая фигура = новый тип фигуры, способы рисования не трогаешь. «Мост» — это как раз это поле-ссылка между двумя иерархиями.
- **В Go (схема):**
```go
type Renderer interface {
    DrawCircle(x, y, r float64)
    DrawRect(x, y, w, h float64)
}

type SVG struct{}    // реализует Renderer
type Canvas struct{} // реализует Renderer

type Circle struct {
    X, Y, R  float64
    Out      Renderer // мост: подставил SVG{} или Canvas{}
}
func (c Circle) Draw() { c.Out.DrawCircle(c.X, c.Y, c.R) }
```
Клиент: `Circle{R: 10, Out: SVG{}}.Draw()` или тот же круг с `Out: Canvas{}` — тип `Circle` один.

### Composite / Компоновщик (Object Tree)
- **Проблема:** дерево: лист и папка; клиент не хочет писать разный код для листа и для узла с детьми.
- **Суть:** и лист, и узел реализуют один интерфейс; у узла в поле — срез детей того же интерфейса. Клиент зовёт один метод у корня, дальше дерево само.
- **В Go:** интерфейс `Node`; `File` / `Dir` с `[]Node`.

### Flyweight / Приспособленец
- **Проблема:** миллионов похожих экземпляров; общие неизменяемые данные в каждом копируются и жрут память.
- **Суть:** общее (шрифт, текстура) хранят в одном разделяемом экземпляре; у «лёгких» объектов в полях только то, что уникально (координаты), а общее передают параметром или берут из кэша по ключу.
- **В Go:** `map[key]*Shared` + клиент передаёт свои координаты отдельно.

## Behavioral (поведенческие)

### Strategy / Стратегия (Policy)
- **Проблема:** один и тот же код должен иногда сортировать по-одному, иногда по-другому (или сжимать zip/gzip) — без огромного `if/switch` внутри и без копипасты всего контекста.
- **Суть:** «как именно считать» выносишь в отдельный тип (или в `func`) с общим интерфейсом, например `Less(a, b) bool`. Контекст держит это в **поле** и при работе зовёт поле, а не конкретный алгоритм. Подставил в поле другой экземпляр — поведение сменилось, сам контекст не переписывал.
- **Пример:** у `Sorter` поле `cmp Comparer`. Один раз создаёшь `Sorter{cmp: ByName{}}`, другой раз `Sorter{cmp: BySize{}}`. Метод `Sort` один и тот же, внутри только `s.cmp.Less(...)`.
- **В Go:** поле/`func` или интерфейс — самый частый паттерн. Не путать с Command: стратегия отвечает на «*как* делать сейчас», а не «положи действие на полку на потом».

### Iterator / Итератор (Cursor)
- **Проблема:** обойти элементы коллекции, не зная (и не светя) как она устроена внутри.
- **Суть:** отдельный тип или функция выдаёт элементы по одному; клиент не лезет в поля слайса/дерева. Параметры обхода скрыты внутри итератора.
- **В Go:** `for range`; `iter.Seq`; метод `All() iter.Seq[T]`.

### Template Method / Шаблонный метод
- **Проблема:** общий каркас алгоритма один, а отдельные шаги у разных вариантов разные.
- **Суть:** один метод задаёт порядок шагов и вызывает «дырки»; конкретные типы (или переданные функции) заполняют только дырки. Клиент зовёт общий метод, не зная деталей шагов.
- **В Go:** нет классического наследования — передают функции-шаги или интерфейс hooks.

### Command / Команда (Action, Transaction)
- **Проблема:** действие нужно не только *сделать*, а ещё *отложить*, положить в очередь, записать в лог, отменить. Обычный вызов метода для этого неудобен.
- **Суть — в чём разница с «голым» вызовом.** Голый вызов: `printer.Print("отчёт.pdf")` — строка кода сработала *прямо сейчас* и исчезла. Её нельзя положить в список «сделать позже», нельзя передать в другой поток, нельзя сделать Undo: вызов уже ушёл, параметров нигде не осталось. Команда: заводишь тип (или замыкание), внутри которого уже лежат и `printer`, и `"отчёт.pdf"`; снаружи у всех команд один метод `Execute()`. Теперь это *значение*: `cmds = append(cmds, PrintCmd{...})`, потом циклом `Execute()`, можно хранить историю для отмены.
- **Пример:**
```go
// голый вызов — только «сейчас»:
printer.Print("a.pdf")

// команда — можно копить и запускать когда удобно:
type Command interface { Execute() }

type PrintCmd struct {
    P    *Printer
    File string
}
func (c PrintCmd) Execute() { c.P.Print(c.File) }

queue := []Command{PrintCmd{printer, "a.pdf"}, PrintCmd{printer, "b.pdf"}}
for _, cmd := range queue { cmd.Execute() }
```
- **В двух словах:** да, на практике часто это просто массив/срез объектов с методом `Execute()` (или срез `func()` — то же самое). Смысл не в массиве, а в том, что **действие стало значением**: его можно копить, тасовать, откладывать, логировать, отменять. Массив — лишь самый частый способ этим пользоваться.
- **В Go:** часто хватает `func()` вместо структуры — это тоже команда: действие упаковано в значение. Strategy выбирает *способ* работы; Command упаковывает *сам факт* «сделай вот это» как объект.

### Observer / Наблюдатель (Dependents, Publish-Subscribe)
- **Суть — от меня** Тоесть интерфейс у Publish должен дать возможность на себя подписаться а потом эти подписки обслужить, а Subscribe выставляет метод который нужно дёрнуть в качестве обслуживания. Подписчик решает, что внутри метода; издатель решает только когда дернуть.
- **Проблема:** у одного объекта изменилось состояние (цена, кнопка нажата) — об этом должны узнать несколько других, причём список слушателей заранее не зашит и может меняться. Нельзя писать в субъекте `ui.Refresh(); logger.Log(); cache.Drop()`: субъект тогда знает слишком много чужих типов.
- **Суть — в двух словах:** субъект не знает *кого* конкретно звать. Он хранит список подписчиков и при изменении орёт всем из списка. Подписчик сам говорит «я хочу слушать» (`Subscribe`) и «я больше не хочу» (`Unsubscribe`). Связь односторонняя и слабая: субъект зависит только от общего интерфейса/`func`, не от `UI`, `Logger` и т.д.
- **Минимально в Go** — даже без интерфейса, срез функций:
```go
type Button struct {
    onClick []func()
}

func (b *Button) Subscribe(fn func()) {
    b.onClick = append(b.onClick, fn)
}

func (b *Button) Click() {
    // «событие случилось» — оповестить всех
    for _, fn := range b.onClick {
        fn()
    }
}

// использование:
btn := &Button{}
btn.Subscribe(func() { fmt.Println("лог: клик") })
btn.Subscribe(func() { fmt.Println("UI: обновить") })
btn.Click() // оба узнали, Button не знает их типов
```
Чуть «классичнее»: интерфейс `Observer { Update() }` и срез `[]Observer` — то же самое, только подписчик — тип, а не `func`.
- **Ещё варианты в Go:** канал на каждого слушателя; общая шина событий. В EIP канал «опубликовал — подписался» — тот же Observer, только между процессами.
- **Не путать с Mediator:** Observer — один источник орёт многим. Mediator — многие общаются *через* одного посредника, а не напрямую.

### State / Состояние
- **Проблема:** поведение экземпляра зависит от режима; `switch` по флагу раздувается.
- **Суть:** каждый режим — отдельный тип с одним интерфейсом; у контекста в поле — текущий экземпляр состояния. Смена режима = подставить в поле другой экземпляр; методы контекста просто делегируют ему.
- **В Go:** интерфейс `State`; или `map[State]Handler`.

### Chain of Responsibility / Цепочка обязанностей (Chain of Command)
- **Проблема:** кто обработает запрос, заранее не ясно; отправитель не должен знать конкретного обработчика.
- **Суть:** либо сам, либо next. есть вызыватель и цепочка обработчиков. Вызыватель зовёт только первого. Тот либо сам отвечает и возвращает результат, либо зовёт следующего и ждёт его ответ — и уже этот ответ отдаёт вызывателю. И так дальше по цепочке. Каждый знает только соседа `next`, не всю очередь.
- **В Go:** поле `next` + `Handle`; или срез обработчиков и цикл; в HTTP — middleware.

### Mediator / Посредник (Controller, Intermediary)
- **Проблема:** много экземпляров ссылаются друг на друга — каждый знает слишком много чужих типов.
- **Суть:** все «коллеги» держат ссылку только на посредника и шлют ему события; посредник уже зовёт нужные экземпляры. Прямых связей «каждый с каждым» нет.
- **В Go:** хаб/`Notify(event)`; шина событий.

### Memento / Хранитель (Token)
- **Проблема:** сохранить состояние экземпляра и потом откатить, не отдавая наружу все его поля.
- **Суть:** сам объект создаёт непрозрачный снимок (отдельный тип, часто неэкспортируемый) и умеет из снимка восстановиться. Хранитель только держит снимок как параметр, внутрь не смотрит.
- **В Go:** `Save() memento` / `Restore(m)`.

### Interpreter / Интерпретатор
- **Проблема:** есть простой язык (фильтр, формула); нужно вычислить выражение.
- **Суть:** каждое правило грамматики — свой тип с методом «вычисли»; из них собирают дерево экземпляров. Корень дерева принимает контекст (переменные) и возвращает результат.
- **В Go:** интерфейс `Expr`; типы `And`, `Or`, `Lit`.

### Visitor / Посетитель
- **Проблема:** над фиксированным набором типов нужна новая операция, а править каждый тип не хочется.
- **Суть:** вводишь тип «посетитель» с методом на каждый конкретный тип; элементы дерева принимают посетителя через `Accept` и вызывают «свой» метод. Новая операция = новый тип посетителя, старые типы данных не трогаешь.
- **В Go:** type switch / visitor; часто проще метод на типе или `ast.Walk`.

## Что в Go почти не копируют 1:1

| GoF | Идиома Go |
|---|---|
| Singleton | DI, `Once`, не глобалы |
| Template Method | функции/hooks, не subclass |
| Abstract Factory | часто хватает `New*` + интерфейсы создаваемых типов |
| Iterator | `range`, `iter.Seq` |
| Prototype | ручной `Clone` / копирование |

Самые «родные» для Go: **Strategy**, **Decorator**, **Adapter**, **Facade**, **Command** (как `func`), **Observer** (каналы), **Factory Method** (как `New`).

## Карта «проблема → паттерн»

| Хочу… | Смотри |
|---|---|
| подменить алгоритм | Strategy |
| обернуть поведение | Decorator / Proxy |
| стыковать чужой API | Adapter |
| упростить подсистему | Facade |
| дерево одинаковых узлов | Composite |
| развязать отправителя и получателя события | Observer / Mediator |
| очередь действий / undo | Command |
| шаг за шагом собрать объект | Builder |
| один из цепочки обработает | Chain of Responsibility |
| поведение по состоянию | State |
