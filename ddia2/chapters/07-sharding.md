# Глава 7. Sharding

- **PDF:** 275–300 (печать 251–276)
- **Якоря:** sharding, partition key, skew, hot spot, key range sharding, hash sharding, mod N, fixed number of shards, hash range, consistent hashing, rebalancing, request routing, coordination service, secondary index, local index, global index, multitenancy, cell-based architecture, pre-splitting, postings list

**Sharding** — разбиение данных на части, когда объём данных или write throughput не помещается на одной машине; это второй (после replication из гл. 6) способ распределения данных. Каждая запись принадлежит ровно одному shard'у; обычно sharding сочетают с replication, так что запись лежит в одном shard'е, но на нескольких узлах (узел может быть leader для одних shard'ов и follower для других). Термин «shard» имеет много имён: partition (Kafka), range (CockroachDB), region (HBase, TiDB), vBucket (Couchbase), vnode (Riak), token-range (Cassandra), tablet (Bigtable, YugabyteDB, ScyllaDB). В PostgreSQL partitioning — разбиение большой таблицы на файлы на одной машине, а sharding — разбиение по машинам; в остальных системах это синонимы. По легенде термин пришёл из Ultima Online (осколки магического кристалла); другая версия — акроним System for Highly Available Replicated Data. Partitioning не имеет отношения к network partition (гл. 9).

Главная причина sharding'а — **scalability**: горизонтальное масштабирование (scale-out) вместо покупки машины побольше. Если не хватает только read throughput — достаточно read scaling из гл. 6; sharding — тяжёлое решение для крупных систем. Он добавляет сложность: нужно выбирать **partition key** (все записи с одним ключом — в одном shard'е); доступ быстрый, только если знаешь shard, иначе — перебор всех shard'ов. Схему sharding'а трудно менять. Легко с key-value данными, тяжело с реляционными (secondary indexes, join'ы между shard'ами); запись в несколько shard'ов требует распределённой транзакции (гл. 8), которая заметно медленнее. Иногда sharding используют и на одной машине — один процесс на ядро CPU (Redis, VoltDB, FoundationDB) ради параллелизма и NUMA.

**Sharding для multitenancy** (SaaS: каждый клиент — tenant с изолированным набором данных). Даёт: resource isolation (дорогая операция одного tenant'а не мешает другим), permission isolation (баг в контроле доступа не «протечёт» между физически разделёнными данными), **cell-based architecture** (сервисы и хранилище группы tenant'ов в автономной ячейке → fault isolation: сбой ограничен ячейкой), per-tenant backup and restore (восстановить одного tenant'а, не задев остальных), regulatory compliance (GDPR/CCPA: экспорт/удаление данных человека = операция над его shard'ом), data residence (shard tenant'а в нужной юрисдикции), gradual schema rollout (миграция схемы tenant за tenant'ом). Проблемы: tenant крупнее одной машины → sharding внутри tenant'а; много мелких tenant'ов → overhead, либо группировка и переезд tenant'ов между shard'ами по мере роста; фичи, соединяющие данные разных tenant'ов (join'ы между shard'ами).

Цель sharding'а — равномерно размазать данные и нагрузку: 10 узлов должны давать ~10× ёмкости и throughput. Неравномерность — **skew**; крайний случай — **hot spot** (shard с непропорциональной нагрузкой; **hot key** — один горячий ключ, например celebrity в соцсети). Алгоритм sharding'а должен позволять rebalancing для снятия hot spots.

**Key range sharding** — каждому shard'у достаётся непрерывный диапазон ключей, как тома бумажной энциклопедии; границы выбирают вручную (Vitess) или автоматически (Bigtable, HBase, range-режим MongoDB, CockroachDB, RethinkDB, FoundationDB). Внутри shard'а ключи отсортированы (B-tree/SSTables) → удобны range scans (пример: сенсоры, ключ — timestamp). Минус: записи в близкие ключи бьют в один shard — все свежие timestamp'ы уходят в shard текущего месяца. Лечение: первым элементом ключа сделать sensor ID (записи размазываются), но range-запрос по времени для многих сенсоров распадается на запросы по каждому сенсору. **Rebalancing** — расщепление shard'а на поддиапазоны при росте (схоже с расщеплением страницы B-tree), слияние при удалении; на пустой БД границы задают заранее (**pre-splitting**, HBase/MongoDB). Split обычно триггерится размером (в HBase по умолчанию 10 GB) или устойчиво высоким write throughput; он дорог — данные переписываются в новые файлы, как compaction, и нагрузка от split'а может перегрузить и без того горячий shard.

**Hash sharding** — если близость ключей не важна (tenant IDs), ключ сначала хешируют: хороший хеш превращает skewed данные в равномерные. Криптостойкость не нужна: MongoDB — MD5, Cassandra/ScyllaDB — Murmur3; встроенные в языки хеши (Java Object.hashCode, Ruby Object#hash) нестабильны между процессами и не годятся. Наивный **mod N** (hash % число узлов) дёшев, но при добавлении узла большинство ключей переезжает — неэффективный rebalancing. **Fixed number of shards** — shard'ов создают много больше, чем узлов (10 узлов, 1000 shard'ов; ключ → hash % 1000, отдельно отслеживается shard→узел); при добавлении узла переносят целые shard'ы, ключи не переезжают. Число shard'ов берут с многими делителями (не только степени 2); мощным узлам дают больше shard'ов. Так работают Citus, Riak, Elasticsearch, Couchbase. Ограничения: узлов не может быть больше, чем shard'ов; неверно выбранное число требует дорогой операции resharding (иногда с остановкой записи); размер shard'а должен быть «just right» — большие shard'ы дорого rebalance'ить, мелкие дают overhead, а при фиксированном числе shard'ов размер растёт вместе с данными.

**Hash range sharding** — когда число shard'ов нельзя предсказать, совмещают key range и hash: shard владеет диапазоном хеш-значений; shard'ы можно расщеплять по мере роста, но range-запросы по partition key неэффективны (ключи разбросаны). Если ключ многоколоночный и shard'ируется только по первой колонке, range-запросы по остальным колонкам работают. Вариант Cassandra/ScyllaDB: пространство хешей делят на диапазоны со случайными границами, по несколько на узел (16 в Cassandra, 256 в ScyllaDB) — дисбалансы усредняются; при добавлении узла соседи передают части диапазонов. Так же устроены YugabyteDB и DynamoDB. Похожая идея в data warehouse: BigQuery (partition key + cluster columns), Snowflake (micro-partitions + cluster keys), Delta Lake — кластеризация улучшает range scans, сжатие и фильтрацию.

**Consistent hashing** — отображение ключей на shard'ы с двумя свойствами: ключей на shard примерно поровну, и при изменении числа shard'ов переезжает минимум ключей. «Consistent» здесь не про replica/ACID consistency, а про склонность ключа оставаться в своём shard'е. Алгоритм Cassandra/ScyllaDB близок к исходному определению; есть варианты: highest random weight (rendezvous hashing), jump consistent hashing — там новому узлу передают отдельные разбросанные ключи, а не поддиапазоны.

Равномерность ключей ≠ равномерность нагрузки: пост celebrity с миллионами подписчиков порождает шторм чтений/записей одного ключа. Лечение: выделить hot key в отдельный shard или даже машину; на уровне приложения — дописывать к ключу случайное число (две цифры → нагрузка на 100 ключей): запись размазывается, но чтения должны собирать и объединять данные из всех 100 ключей, плюс bookkeeping о том, какие ключи расщеплены; нагрузка меняется во времени (вирусный пост «остывает»), ключ может быть горячим только на запись или только на чтение. Amazon называет автоматическую борьбу с hot shards heat management / adaptive capacity.

**Rebalancing: автоматический vs ручной.** Автоматика удобна и умеет autoscale (DynamoDB — минуты), но непредсказуема: rebalancing дорог, может перегрузить сеть/узлы, а при near-max write throughput split может не поспевать за записями. Опасно сочетать с automatic failure detection: перегруженный (медленный) узел признают мёртвым, снимают с него нагрузку → перегруз других узлов → cascading failure. Поэтому человек в цикле полезен: медленнее, но без сюрпризов; ручной rebalancing хорош превентивно перед известными всплесками (Cyber Monday, билеты на ЧМ). Средний вариант: система предлагает план (Couchbase, Riak), администратор подтверждает.

**Request routing** — как клиенту узнать узел для ключа; похоже на service discovery, но в отличие от stateless сервисов запрос к ключу может обслужить только узел с replica нужного shard'а. Три схемы: (1) клиент шлёт любому узлу, тот форвардит; (2) routing tier — shard-aware load balancer (не хранит данные); (3) клиент сам знает shard→узел и ходит напрямую. Вопросы: кто решает shard→узел (единственный coordinator — как его сделать fault-tolerant и не допустить split brain), как routing-компоненты узнают об изменениях, что с in-flight запросами при переезде shard'а (cutover). Обычно используют **coordination service**: ZooKeeper (HBase, SolrCloud), etcd (Kubernetes), у MongoDB — config server + mongos, у Kafka/YugabyteDB/TiDB/ScyllaDB — встроенный Raft; Riak вместо consensus — gossip-протокол: слабее, возможен split brain, что терпимо для leaderless БД. IP-адреса клиенты находят через DNS (они меняются реже, чем shard→узел). Это логика OLTP; аналитические БД обычно исполняют запрос по всем shard'ам параллельно (гл. 11).

**Secondary indexes и sharding.** Индекс не ложится на shard'ы аккуратно; два подхода (пример книги — продажа подержанных машин, индекс color:red). **Local index** (document-partitioned): каждый shard индексирует только свои записи (ведёт свой postings list). Плюс: запись трогает один shard. Минус: поиск без известного partition key идёт во все shard'ы (scatter-gather) — дорого, tail latency amplification, добавление узлов не растит query throughput. Используют MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, VoltDB. Предупреждение: самодельный индекс в коде приложения легко рассинхронизировать race conditions и частичными сбоями записи. **Global index** (term-partitioned): индекс покрывает все shard'ы и сам shard'ируется по значению (терму) — хешем или диапазоном. Плюс: запрос с одним условием читает один shard (сами записи — всё равно из многих). Минус: запись обновляет несколько index-shard'ов → нужна распределённая транзакция или асинхронность (в DynamoDB глобальные индексы обновляются асинхронно — чтения могут быть stale); пересечение длинных postings list'ов для AND-запроса требует пересылки по сети. Используют CockroachDB, TiDB, YugabyteDB; DynamoDB поддерживает оба типа. Глобальные индексы хороши, когда read throughput выше write.

Итог главы (Summary): sharding нужен, когда данные не помещаются на одну машину; цель — равномерная нагрузка без hot spots, для чего выбирают схему под данные и rebalance'ят при смене состава узлов. Два подхода: key range (эффективные range queries, риск hot spots, рост через split диапазона) и hash (равномернее, но range queries неэффективны; типично — фиксированное число shard'ов, перенос целых shard'ов между узлами). Частый приём: первая часть ключа — partition key, остальное — сортировка внутри shard'а, тогда range queries в пределах ключа работают. Для маршрутизации запросов обычно нужен coordination service; secondary index тоже нужно shard'ировать — локально (пишем в один shard, читаем из всех) или глобально (пишем в несколько, читаем из одного). Каждый shard работает в основном независимо — это и даёт масштабирование, но операции записи в несколько shard'ов (один успех, другой сбой) — тема следующих глав.
