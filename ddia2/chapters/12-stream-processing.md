# Глава 12. Stream Processing

- **PDF:** 511–562 (печать 487–538)
- **Якоря:** event streams, message broker, backpressure, load balancing, fan-out, log-based brokers, consumer offsets, log compaction, CDC, Event Sourcing, dual writes, outbox pattern, immutability, changelog, CEP, stream analytics, watermarking, stream joins, exactly-once, checkpointing

Глава 11 предполагала **bounded** входы: batch знает, когда вход закончился, поэтому MapReduce-сортировка требует весь вход заранее. В реальности данные неограниченны: пользователи производили их вчера, производят сегодня и будут завтра — dataset никогда не «завершён». Batch режет поток на искусственные куски (день, час), но отражение изменений через сутки — слишком медленно; обрабатывать каждое событие по мере появления и есть **stream processing**. Stream — данные, инкрементально доступные во времени (stdin/stdout Unix, TCP, lazy lists, FileInputStream).

**Event streams:** event — аналог record из batch: маленький самодостаточный **immutable** объект с timestamp о факте из прошлого (клик, покупка, показание сенсора, строка веб-лога). Продюсер (publisher/sender) генерирует событие один раз, обрабатывают многие потребители (subscribers/recipients); связанные события группируются в **topic/stream** — стриминговый аналог файла. Периодический polling хранилища дорог (чем чаще, тем меньше доля новых событий) — лучше уведомления, а БД-триггеры для этого слабы; так появились messaging systems.

**Messaging:** продюсер шлёт сообщение, его пушат потребителям. Два вопроса различают системы: (1) продюсеры быстрее потребителей — три ответа: drop, буферизация в очереди или **backpressure** (flow control; так работают Unix pipe и TCP: фиксированный буфер, отправитель блокируется); (2) крахи/офлайн узлов — теряются ли сообщения; durability стоит комбинации записи на диск и/или replication, ценой throughput/latency (для метрик потеря приемлема, для счётчиков — нет). Batch даёт сильную гарантию retry+discard; в стриминге её ещё предстоит построить. Прямая доставка (UDP multicast на биржах, ZeroMQ/nanomsg, StatsD по UDP, **webhooks** — HTTP-callback) требует постоянно онлайн клиентов: offline-потребитель пропускает сообщения, а буфер ретраев гибнет вместе с продюсером.

**Message broker** (message queue) — «БД, оптимизированная под потоки сообщений»: сервер с клиентами, централизация данных переживает disconnect/крахи клиентов, durability переносится на брокера, slow consumers → неограниченная очередь вместо drop/backpressure. Доставка асинхронна: продюсер ждёт лишь подтверждения буферизации. Отличия от БД: брокер удаляет сообщение после доставки (не для долгого хранения), предполагает малый рабочий набор, не умеет произвольных запросов, но уведомляет об изменениях; БД держит данные до явного удаления и отвечает на запросы по snapshot. Стандарты **JMS/AMQP**: RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO, IBM MQ, Azure Service Bus, Google Cloud Pub/Sub.

**Load balancing vs fan-out:** load balancing — каждое сообщение одному из потребителей (AMQP-очередь, JMS shared subscription) — параллелизм обработки; **fan-out** — каждое сообщение всем (JMS topics, AMQP exchange bindings) — стриминговый аналог нескольких batch-джобов над одним файлом. Kafka **consumer groups** комбинируют оба паттерна: внутри группы — balancing, между группами — fan-out.

**Acks and redelivery:** потребитель явно подтверждает обработку; без ack брокер доставляет сообщение другому. Но load balancing + redelivery неизбежно переупорядочивает (упавший m3 доставляется после m4): при причинных зависимостях нужна отдельная очередь на потребителя. Сообщение с битым содержимым (нет обязательного ключа) валит каждого потребителя бесконечно — спасают **dead letter queues (DLQ)**: битые сообщения откладывают, мониторят, оператор чинит код или дропает.

**Log-based message brokers** (Apache Kafka, Amazon Kinesis Streams; Google Cloud Pub/Sub похож, но с JMS-API): гибрид durable storage БД и low-latency уведомлений. Log — append-only последовательность записей на диске: продюсер дописывает в конец, потребитель читает последовательно (как `tail -f`). Топик шардируется на **partitions**; внутри партиции монотонный **offset** даёт total order, между партициями порядка нет — события одного пользователя шлют в одну партицию (user ID как partition key). Fan-out тривиален (чтение не удаляет); load balancing — назначением целых шардов узлам: параллелизм ≤ числа шардов, одно медленное сообщение тормозит весь шард (**head-of-line blocking**).

**Consumer offsets:** вместо ack на каждое сообщение — периодическая запись смещения (как log sequence number в репликации: брокер = leader, потребитель = follower); после краха чтение с последнего записанного offset → часть сообщений обработается дважды. Старые сегменты лога удаляются/архивируются (диск — большой кольцевой буфер: 20 TB / 250 MB/s ≈ 22 часа при полной скорости, обычно дни-недели); сильно отставший потребитель теряет сообщения, но только он сам — production не страдает, можно спокойно экспериментировать. Tiered storage переносит старые сообщения в object storage (Kafka, Redpanda), WarpStream и Bufstream хранят всё в объектном хранилище — дешевле и удобнее для batch-интеграции.

**Replaying old messages:** потребление read-only, offset под контролем потребителя — можно перезапустить потребителя со вчерашнего offset и перепроцессить день заново, сколько угодно раз с другим кодом. Это возвращает главное свойство batch: отделение derived data от input, эксперименты и восстановление после багов.

**Keeping systems in sync:** ни одна система не покрывает все нужды (OLTP + кеш + full-text index + warehouse) — копии надо синхронизировать. **Dual writes** (приложение пишет в БД и индекс) страдают от гонок: клиенты пишут X=A и X=B, порядки в БД и индексе расходятся навсегда (рис. 12-4) — и от частичных отказов (нужен atomic commit). Решение: одна БД — leader, остальные — follower'ы через **CDC (Change Data Capture)**: ловить все изменения, извлекать их потоком и применять к derived systems в том же порядке (гонка рис. 12-4 исчезает). Репликационный лог долго был внутренней деталью БД; теперь есть логическая (row-based) репликация и инструменты: **Debezium** (MySQL, PostgreSQL, Oracle, SQL Server, Db2, Cassandra), Kafka Connect, Maxwell (binlog), GoldenGate, pgcapture. CDC асинхронен — все проблемы replication lag; полную историю не хранят, поэтому нужен **initial snapshot**, согласованный с позицией в логе (Debezium — алгоритм watermarking от Netflix DBLog).

**Log compaction:** оставлять только последнюю запись по ключу (tombstone = удаление). Компакт-лог содержит текущее состояние БД целиком → новый derived system стартует с offset 0 без снапшота. Поддержка в Kafka; позволяет брокеру быть durable storage, а не только транзитной почтой.

**CDC vs Event Sourcing:** CDC — БД остаётся mutable, лог извлекается низкоуровнево из replication log; добавить к существующей БД почти без изменений. **Event Sourcing** — приложение явно строится на immutable событиях уровня бизнес-намерений, append-only event store, update/delete запрещены. CDC-событие несёт всю новую версию записи → log compaction возможен; события ES не перекрывают друг друга → нужна вся история (snapshots — лишь оптимизация чтения/восстановления).

**CDC and schemas:** CDC выставляет внутреннюю схему наружу — удаление колонки ломает потребителей вплоть до customer-facing outage; помогают data contracts и **outbox pattern**: отдельные таблицы-«исходящие» со стабильной схемой, записываются в одной транзакции с бизнес-данными (dual write без его проблем: обе записи в одной системе). Цена: поддержка трансформации между схемами и лишний объём записи в хранилище.

**State, streams, immutability:** изменяемое состояние и append-only лог не противоречат друг другу — это две стороны одной медали: состояние есть «интеграл» потока событий по времени, **changelog** — «производная» состояния. Gray/Reuter (1992): «нет фундаментальной нужды хранить БД — в логе есть всё; БД нужна лишь для скорости выборок». Бухгалтерия веками жила по этому принципу: ошибку не стирают, а добавляют компенсирующую проводку (audit trail). **Immutability** упрощает диагностику и восстановление после багов и хранит больше, чем текущее состояние (положил в корзину и убрал — потерянная в БД информация, полезная для аналитики).

**Deriving views from the log:** один лог → несколько read-optimized представлений (Druid пьёт из Kafka напрямую, Kafka Connect sink'и — в БД/индексы): новая фича получает собственное view рядом со старым без миграции. Споры о нормализации/денормализации теряют смысл: денормализуй в read view — лог держит их согласованными. Минус CQRS: view обновляются асинхронно — проблема read-your-writes. Плюс: событие — самодостаточное описание действия пользователя, одно атомарное дописывание в лог; при одинаковом шардировании лога и состояния однопоточный потребитель обходится без concurrency control (как actual serial execution).

**Limitations of immutability:** при высокой churn (много update/delete на малом наборе) история разрастается, compaction/GC становятся критичны; GDPR и утечки требуют настоящего удаления — события «считать удалённым» мало, нужно переписать историю (Datomic — excision, Fossil — shunning). По-настоящему удалять трудно: копии повсюду, SSD и бэкапы любят append-only. **Crypto-shredding** — шифровать и забыть ключ: данные остаются, но нечитаемы; ограничения: ключи на группу данных (всё-или-ничего), puncturable encryption (выборочный отзыв) пока редкость. Удаление — скорее «сделать труднодоступным», чем «невозможным».

**Processing streams:** три варианта — (1) писать события в БД/кеш/индекс, (2) пушить людям (alerts, dashboards), (3) операторы (operator/job), превращающие input streams в output streams, как Unix-процессы и MapReduce-джобы. Разница с batch: поток не кончается — сортировка бессмысленна (нет sort-merge join), fault tolerance другой: рестарт с начала неприемлем для джобы, работающей годы. Классика применения — **fraud detection**: детект неожиданной смены паттернов использования карты и блокировка при подозрении на кражу; также trading, мониторинг производства, военные системы.

**CEP (Complex Event Processing)** — поиск паттернов событий, как регулярное выражение ищет паттерны в строке; декларативный SQL-подобный язык или GUI (Esper, Apama, TIBCO StreamBase; SQL в Flink и Spark Streaming). Роли данных и запросов перевёрнуты: БД хранит данные и забывает запросы, CEP хранит standing queries и прогоняет через них события. **Stream analytics** — агрегаты и статистика по окнам (rate события, rolling average, сравнение с тем же временем прошлой недели); вероятностные алгоритмы (Bloom filters, HyperLogLog, оценки перцентилей) экономят память — приблизительность это оптимизация, а не свойство streaming. Фреймворки: Apache Storm, Spark Streaming, Flink, Samza, Beam, Kafka Streams; hosted — Google Cloud Dataflow, Azure Stream Analytics.

**Materialized views:** держать кеши/индексы/warehouse в актуальном состоянии из changelog — нужно окно «до начала времён»; Kafka Streams и ksqlDB строят это на log compaction. Обычные БД обновляют MV батчем (PostgreSQL REFRESH MATERIALIZED VIEW) — пересчёт всего (неэффективно) и несвежесть. **IVM (incremental view maintenance)** — инкрементальный пересчёт только изменённого: Materialize, RisingWave, ClickHouse, Feldera (SQL-запросы как инкрементальные операторы). **Search on streams** — наоборот относительно обычного поиска: запросы хранятся, документы проверяются на лету (Elasticsearch percolator; индексировать можно и запросы). Акторные системы — не stream processing: акторы про concurrency-механизм (ephemeral, one-to-one, произвольные циклы), стримы про data management (durable, multi-subscriber, ацикличные пайплайны); пересечение — Storm distributed RPC.

**Reasoning about time.** Batch доверяет только timestamp'ам событий (детерминизм); stream-фреймворки часто окнуют по **processing time** (системным часам) — просто, но ломается при lag: redeploy и разбор backlog создают ложный всплеск запросов. События приходят не по порядку (аналогия Star Wars: дата выхода ≠ номер эпизода) — алгоритмы должны это учитывать. **Stragglers** — события, пришедшие после закрытия окна: либо игнорировать (с метрикой дропов), либо публиковать correction/retraction. **Watermarking** — специальное сообщение «событий раньше t больше не будет» (DBLog); при нескольких продюсерах порог отслеживается на каждого. Часам устройства доверять нельзя: три timestamp'а (произошло/отправлено с часов устройства, получено с часов сервера) дают оценку смещения часов.

**Windows:** **tumbling** (фиксированная длина, каждое событие ровно в одном окне), **hopping** (фиксированная длина с перекрытием и шагом hop — сглаживание), **sliding** (все события в пределах интервала друг от друга; реализуется буфером, отсортированным по времени), **session** (события одного пользователя до паузы, например 30 минут — sessionization для веб-аналитики). Окна и joins держат state: счётчик — O(1), sliding/joins буферизуют события — большие окна и высокая пропускная способность требуют ёмкости под state.

**Stream joins.** **Stream–stream (window join):** search-события и click-события одного session ID в пределах окна (час) — для честного click-through rate нужны оба потока (вложение поиска в клик теряет «неклики»); state — индекс событий окна, при истечении окна emit «не кликнуто». **Stream–table (enrichment):** activity events обогащаются профилями; remote lookup медленен — локальная копия (hash join), обновляемая подпиской на changelog через CDC; окно таблицы — «с начала времён», новые версии перезаписывают старые. **Table–table (materialized view maintenance):** timeline-кеш = join постов и follows; поток изменений join'а подчиняется product rule (u·v)′ = u′v + uv′.

**Time dependence of joins:** порядок событий между шардами не определён → join недетерминирован (повторный прогон даёт другой результат). В warehouses это **SCD (slowly changing dimension)**: версионировать запись (каждый tax rate получает новый id, счёт хранит id версии) — join детерминирован, но log compaction невозможен; либо денормализовать ставку прямо в событие продажи.

**Fault tolerance.** Batch: рестарт задачи, отброс частичного вывода, immutable входы → эффект **exactly-once** (точнее **effectively-once**: записи могут обрабатываться повторно, но видимый результат — как при одной обработке). Stream не кончается — «дождаться завершения задачи» нельзя. **Microbatching** (Spark Streaming, ~1 сек — компромисс между overhead и задержкой; неявно даёт tumbling window по processing time) и **checkpointing** (Flink: rolling checkpoints состояния в durable storage, рестарт с последнего чекпойнта, отброс вывода после него; барьеры в потоке вместо границ микробатчей) дают exactly-once внутри фреймворка — но внешние side effects (email, запись в БД, публикация наружу) при рестарте повторятся.

**Atomic commit revisited:** все выводы и эффекты обработки события (сообщения дальше, записи в БД, изменение operator state, сдвиг consumer offset) должны зафиксироваться атомарно. XA поверх гетерогенных систем дорог; но внутренние транзакции фреймворка (Google Cloud Dataflow, VoltDB, Kafka) эффективны — транзакции не выходят за пределы системы, протокол амортизируется пачкой сообщений на транзакцию. **Idempotence:** повтор операции = тот же эффект (delete ключа — да, increment — нет); операцию можно сделать идемпотентной метаданными — писать вместе со значением offset сообщения и пропускать повторный update (идея Storm Trident). Условия: replay тех же сообщений в том же порядке (log-based брокер), детерминизм обработки, нет конкурентных писателей, fencing при failover.

**Rebuilding state after a failure:** state (оконные агрегаты, таблицы для joins) надо восстанавливать: remote datastore медленен; локальный state + периодическая репликация — Flink пишет снапшоты в distributed filesystem, Kafka Streams реплицирует изменения состояния в log-compacted топик, VoltDB избыточно обрабатывает каждое сообщение на нескольких узлах. Иногда репликация не нужна: короткие окна пересчитываются реплеем входных событий, локальная копия БД — из log-compacted changelog.

**Summary.** Stream processing = batch, но непрерывно, над unbounded входом; message brokers и event logs — стриминговый аналог файловой системы. **AMQP/JMS-брокер:** назначение отдельных сообщений, ack, удаление после обработки — как асинхронный RPC (task queue: порядок не важен, перечитывать не нужно). **Log-based брокер:** шарды целиком одному узлу, порядок сохранён, прогресс — checkpointing offset'а, сообщения остаются на диске — можно вернуться и перечитать. Записи в БД — тоже поток: changelog через CDC (неявно) или Event Sourcing (явно); log compaction хранит полную копию БД. Отсюда — синхронизация derived systems (индексы, кеши, аналитика), построение свежих view с нуля, stream joins и fault tolerance. Назначения: CEP (паттерны событий), stream analytics (оконные агрегаты), materialized views (актуальность derived data). Трудности времени: processing time vs event timestamps, stragglers. Joins: stream–stream (связанные события в окне), stream–table (обогащение через changelog), table–table (инкрементальное поддержание MV). Fault tolerance: microbatching, checkpointing, transactions, idempotent writes.
