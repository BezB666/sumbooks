# Глава 8. Transactions

- **PDF:** 301–368 (печать 277–344)
- **Якоря:** transaction, ACID, atomicity, durability, dirty read, dirty write, read committed, snapshot isolation, MVCC, repeatable read, read skew, lost update, write skew, phantom, serializability, two-phase locking (2PL), serializable snapshot isolation (SSI), predicate lock, two-phase commit (2PC), exactly-once semantics

**Transaction** — группировка чтений/записей в логическую единицу: либо commit, либо abort/rollback, после abort можно безопасно повторить. Это не закон природы, а инструмент упрощения программирования: БД берёт на себя обработку части сбоев и гонок (safety guarantees), приложение может их игнорировать. Отсутствие ACID, вероятно, стало технической причиной скандала Post Office Horizon. NoSQL в конце 2000-х выбросили транзакции ради масштабируемости, но NewSQL (CockroachDB, TiDB, Spanner, FoundationDB, YugabyteDB) показали: sharding + consensus дают сильный ACID на масштабе. Не каждому приложению нужны транзакции — иногда ослабление гарантий выгодно ради производительности или доступности.

**ACID** (термин 1983 г., Härder и Reuter) на практике размыт: "ACID compliant" — почти маркетинг; BASE = "не ACID". По буквам:

**Atomicity** — не про конкурентность, а про all-or-nothing при сбое: abort откатывает все сделанные записи (точнее было бы назвать abortability). **Consistency** — слово с пятью разными смыслами; в ACID это инварианты приложения, объявленные как constraints (FK, uniqueness, check, иногда triggers/materialized views); сложные инварианты БД не умеет — их соблюдение обязанность приложения.

**Isolation** — конкурентные транзакции не мешают друг другу; идеал — serializability, но у неё performance cost (Oracle "serializable" на деле лишь snapshot isolation). **Durability** — после commit данные не пропадут (fsync, write-ahead log, checksums); совершенной durability нет: баги прошивок SSD, потеря питания, корреляция сбоев; есть только risk-reduction — диск + реплики + бэкапы вместе.

Одиночный объект: storage engine почти всегда даёт atomicity/isolation на уровне одной записи (лог для восстановления, lock на объект); atomic increment и conditional write (CAS) убирают read-modify-write.

Но нужны и multi-object transactions: foreign keys, денормализованные документы (счётчик непрочитанных писем расходится с самим письмом), secondary indexes. Retry abort'а безопасен, но с оговорками: commit мог пройти, а ответ потеряться (нужна дедупликация); retry при перегрузке усугубляет проблему (exponential backoff); побочные эффекты вне БД (отправка email) не откатываются; постоянные ошибки (constraint violation) ретраить бессмысленно.

**Read committed** (дефолт в Oracle, PostgreSQL, SQL Server): читаешь только committed (no dirty reads), не перезаписываешь uncommitted (no dirty writes). Реализация: row-level write locks; dirty reads гасятся отдачей старого committed-значения, пока пишущая транзакция не закоммитится. Read uncommitted ещё слабее. Но read committed допускает **Read skew** (nonrepeatable read): Алия читает два своих счёта в момент перевода $100 — видит $900 вместо $1000; терпимо в UI, катастрофично для backup и аналитических/integrity-запросов.

**Snapshot isolation / repeatable read**: каждая транзакция читает consistent snapshot на момент старта. Реализация — **MVCC**: монотонный txid, поля inserted_by/deleted_by, update = delete+insert, версии строк лежат рядом и чистятся GC; правила видимости — видно то, что закоммичено до старта читателя и не удалено до его старта, записи aborted/более поздних транзакций невидимы. Ключевой принцип: readers never block writers, writers never block readers. Путаница имён: PostgreSQL "repeatable read" = snapshot isolation, в MySQL — слабее, в Db2 — serializability; SQL standard не знает snapshot isolation, поэтому определение repeatable read расплывчато. Альтернатива MVCC — immutable copy-on-write B-trees (CouchDB, Datomic, LMDB).

**Lost update**: два read-modify-write затирают друг друга (счётчик 42→43 вместо 44 при двух инкрементах). Решения: atomic write operations (UPDATE ... SET value = value + 1 — лучший вариант, где применим; ORM часто подсовывают небезопасные read-modify-write); explicit locking (SELECT ... FOR UPDATE — риск забытых локов и deadlock); автоматическое обнаружение (PostgreSQL repeatable read, Oracle serializable, SQL Server snapshot — но не MySQL InnoDB); conditional write / compare-and-set с version column (optimistic locking); в multi-leader/leaderless репликации — merge конфликтов и CRDT для коммутативных операций (LWW теряет обновления).

**Write skew**: пример врачей on-call — Алия и Брайс одновременно уходят с дежурства, каждый видит "нас двое", оба коммитят, на смене никого. Не dirty write и не lost update: гонка через два разных объекта; обобщение lost update. Слабые уровни его не ловят; спасает serializable или SELECT FOR UPDATE по строкам-предпосылкам (здесь это работает, т.к. строки существуют). Ещё примеры: бронь переговорки на пересекающиеся интервалы, ход фигурой на занятую клетку, регистрация username (спасает uniqueness constraint), двойное списание денег.

**Phantom**: write одной транзакции меняет результат SELECT другой, но лочить нечего — проверяется *отсутствие* строк (нет броней, имя свободно). Snapshot isolation защищает только read-only запросы. Костыль — materializing conflicts: таблица-заглушка (слоты комнат/времени), по которой можно взять FOR UPDATE; работает, но уродливо, error-prone, concurrency control протекает в модель данных — last resort.

**Serializability** — сильнейший уровень; три реализации. (1) **Actual serial execution**: одна транзакция за раз в одном потоке; стало возможно в 2000-е — RAM подешевела, OLTP-транзакции короткие, аналитика уходит на snapshot. Требует stored procedures (VoltDB/Java, Datomic/Java-Clojure, Redis/Lua, MongoDB/JS) — минусы: неудобные языки, сложность деплоя/дебага, риск для общей БД. Масштабируется sharding'ом: single-shard транзакции линейно, cross-shard — lockstep-координация, на порядки медленнее (VoltDB ~1000 cross-shard записей/с).
(2) **Two-phase locking (2PL)** — 30 лет был стандартом (не путать с 2PC!): shared/exclusive locks на объекты, writers block readers и наоборот; фазы роста и сжатия не пересекаются — локи держатся до commit/abort. Deadlock'и часты, БД автоматически откатывает жертву. Минус — производительность: нестабильная latency, одна медленная транзакция стопорит всё. Против фантомов — **Predicate locks** (дорого: проверка всех условий) или аппроксимация index-range locks / next-key locking (лок на индексную запись или диапазон; нет индекса — лок на всю таблицу).
(3) **Serializable snapshot isolation (SSI)** (2008) — оптимистичный подход: транзакции не блокируются, при commit проверяется, действовала ли транзакция на устаревшей предпосылке (outdated premise). Детектируется два случая: stale MVCC reads (прочитанная версия обошла видимость, но позже закоммитилась) и writes affecting prior reads (запись бьёт по index entry, который недавно читали — tripwire вместо блокировки; первый коммит проходит, второй abort'ится). Проигрывает при высокой contention (много abort'ов и повторной работы), выигрывает предсказуемой latency и масштабируемостью (FoundationDB). Используется в PostgreSQL serializable, CockroachDB, FoundationDB, SQL Server Hekaton.

**Distributed transactions**: на одном узле атомарность даёт commit record в WAL — commit point это запись на диск. На многих узлах commit на одних и abort на других = несогласованность (закоммиченное уже видно другим транзакциям и не отзывается); задача — atomic commitment. **Two-phase commit (2PC)**: coordinator + participants; phase 1 — prepare (участник пишет всё на диск и голосует yes/no), phase 2 — commit или abort всем; координатор пишет решение в свой лог (commit point) и retry forever. Две точки невозврата: сказавший yes обещает закоммититься; решение координатора необратимо (аналогия с брачной церемонией: после "I do" отказ невозможен). Уязвимость — coordinator failure: проголосовавшие участники застревают **in doubt**, держат row locks и не могут ни commit, ни abort сами; восстановление только через лог координатора, потеря лога = ручное разрешение. 2PC — blocking protocol; 3PC требует bounded delay и в реальных сетях не гарантирует атомарности; правильное решение — fault-tolerant consensus (глава 10).

**XA** (1991) — C API для 2PC поверх гетерогенных технологий (JTA, MSDTC, JMS). Проблемы: coordinator в процессе приложения = single point of failure (и его лог — часть durable state); участники общаются только через приложение и драйверы; lowest common denominator — нет deadlock detection и SSI между системами; orphaned in-doubt transactions держат локи вечно, а heuristic decisions = "probably breaking atomicity". Внутренние distributed transactions NewSQL-баз этих бед лишены: координатор и шарды реплицируются, есть прямые каналы и consensus.

**Exactly-once semantics**: атомарный commit ack'а брокера + записей в БД в одной распределённой транзакции. Но можно проще — идемпотентность внутри одной БД: таблица обработанных message ID, проверка/вставка ID в транзакции, ack после commit; retry увидит ID и отбросит дубль. Достаточно обычных транзакций в БД (так делает Kafka Streams); распределённый commit не обязателен.

**Summary**: транзакции — абстракция, позволяющая приложению делать вид, что части сбоев и гонок не существует; большой класс ошибок сводится к abort + retry. Простые паттерны доступа (одна запись) живут без транзакций; для сложных — без них данные (например, денормализованные) легко рассинхронизируются. Слабые уровни защищают от части аномалий, остальное — вручную (explicit locking); только serializable закрывает всё.

Три реализации serializable: serial execution (быстрые stored procedures, одна CPU-шина или sharding), 2PL (простой, но медленный), SSI (оптимистичный, без блокировок, abort при несериализуемом исполнении). Атомарность на многих узлах — 2PC: внутри одной БД работает неплохо, через XA между разными технологиями проблематичен; идемпотентность даёт exactly-once без распределённого commit. Транзакции ценны при любой модели данных, не только реляционной.
