# Глава 5. Encoding and Evolution

- **PDF:** 185–220 (печать 161–196)
- **Якоря:** encoding, decoding, schema evolution, backward compatibility, forward compatibility, rolling upgrade, JSON, XML, Protocol Buffers, field tags, Avro, writer's schema, reader's schema, REST, RPC, gRPC, OpenAPI, durable execution, message broker, actor model

Всё меняется: новые фичи тянут за собой новые данные, а значит и код. Менять код мгновенно нельзя — на серверах делают **rolling upgrade** (новая версия понемногу, без downtime), клиенты обновляются когда попало. Поэтому старые и новые версии кода и данных сосуществуют, и нужны два свойства: **backward compatibility** (новый код читает данные старого) и **forward compatibility** (старый код читает данные нового). В API это переворачивается по направлениям: старый клиент → новый сервис = backward на request + forward на response; новый клиент → старый сервис = наоборот. Backward даётся легко (новый автор знает старый формат), forward — сложнее: старый код обязан *сохранять* непонятные ему поля при decode→modify→encode, иначе данные теряются (рис. 5-1).

**Encoding** (serialization, marshaling) — перевод in-memory объектов в самодостаточную последовательность байт; **decoding** (parsing, deserialization, unmarshaling) — обратно. Термин serialization перегружен (в транзакциях, гл. 8 — другой смысл), поэтому в книге — encoding. Иногда конверсия вообще не нужна: zero-copy форматы Cap'n Proto и FlatBuffers работают и в памяти, и на диске/в сети.

Языковые кодировки (java.io.Serializable, Python pickle, Ruby Marshal, Kryo) удобны, но порочны: привязка к одному языку; decode инстанцирует произвольные классы — дыра для удалённого исполнения кода; версионирование и эффективность — запоздалая мысль. Годятся только для очень короткоживущих данных.

**JSON, XML, CSV** — текстовые, вездесущие, но с изъянами: XML многословен; с числами беда — JSON не различает int/float и не задаёт precision, в JavaScript целые больше 2^53 портятся (X/Twitter отдаёт 64-битный post ID дважды — числом и строкой); бинарных строк нет, костыль Base64 даёт +33% размера; XML Schema и JSON Schema сложны в изучении; CSV без схемы и с размытым escaping (RFC 4180 соблюдают не все парсеры). И всё же как data interchange между организациями они останутся: договориться о формате важнее его красоты. **JSON Schema** стал стандартом моделирования данных (OpenAPI, Confluent Schema Registry, Apicurio Registry, pg_jsonschema, MongoDB $jsonSchema): open content model (additionalProperties: true по умолчанию — схема описывает скорее, что *запрещено*) vs closed; есть patternProperties, if/else, ссылки на внешние схемы — мощно, но громоздко, и эволюционировать такие схемы совместимо трудно.

Бинарные варианты JSON (MessagePack, CBOR, BSON, Smile…) и XML (WBXML, Fast Infoset) компактнее, но имена полей остаются в данных: пример MessagePack — 66 байт против 81 у текстового JSON, выигрыш скромный.

**Protocol Buffers** (и Thrift): обязательная схема в IDL + кодогенерация. В данных нет имён полей — только **field tags** (номера 1, 2, 3), тип и тег пакуются в один байт; variable-length integers (1337 → 2 байта); массивов нет — repeated это повтор того же тега. Правила **schema evolution**: имя поля менять можно (в данных его нет), тег — нельзя; новое поле = новый тег, старый код его просто пропускает (аннотация типа позволяет перепрыгнуть нужное число байт и не потерять поле); удалённый тег никогда не переиспользовать, резервировать в схеме; отсутствующее поле заполняется default-значением. Смена типа рискованна: int32→int64 старый код может обрезать (truncation).

**Avro** (с 2009, вырос из Hadoop): тоже схема (IDL для людей, JSON для машин), но без тегов — 32 байта, самый компактный. Данные — просто конкатенация значений (строка = длина + UTF-8), без схемы не разобрать. Поэтому decode идёт по двум схемам: **writer's schema** (то, чем писали) и **reader's schema** (то, чего ждёт читатель); resolution сопоставляет поля по *именам*, лишние игнорирует, недостающие берёт default из reader's schema. Добавлять/удалять можно только поля с default (иначе ломается backward/forward); null — только через union, причём null первым (явность вместо «billion dollar mistake»); переименование — через aliases (backward, но не forward); новая ветка union — тоже backward-only. Где брать writer's schema: object container file (схема раз в начале файла); БД — номер версии в каждой записи + реестр схем (Kafka + Confluent Schema Registry, LinkedIn Espresso); сеть — договариваются при соединении (Avro RPC). Плюс Avro: дружелюбен к динамически сгенерированным схемам — дамп реляционной БД генерит схему сам, поля матчатся по именам; в protobuf теги пришлось бы вести руками.

Достоинства schema-based бинарных кодировок: компактнее binary-JSON (нет имён полей); схема = всегда актуальная документация; реестр схем = проверка совместимости до деплоя; кодогенерация = compile-time type checking. Идея не нова — это ASN.1 (1984; DER и сейчас в X.509). Schema evolution даёт гибкость schemaless JSON плюс гарантии и тулинг.

Modes of dataflow. Через БД: пишущий кодирует, читающий декодирует — «сообщение самому себе в будущем», backward обязателен; при rolling upgrade одновременно работают разные версии — нужен и forward. **Data outlives code**: данные пятилетней давности лежат в старом формате; миграции дороги и откладываются (LSM-tree переписывает данные при compaction; реляционки добавляют nullable-колонку без rewrite, null'ы подставляются при чтении), сложные изменения (single-valued → multivalued) всё равно требуют rewrite на уровне приложения. Архивный дамп пишется одним куском в свежей схеме — Avro object container files, для аналитики Parquet.

Через сервисы (**REST, RPC**): в отличие от произвольных запросов к БД сервис отдаёт только заранее заданные API — инкапсуляция; цель microservices — независимый деплой и эволюция. Web service — HTTP как транспорт; REST — URL как ресурсы, HTTP для кеша, аутентификации, content negotiation. IDL: **OpenAPI** (Swagger) для JSON, protobuf для **gRPC**; фреймворки: FastAPI — код первичен, IDL генерится; gRPC — IDL первичен, генерится код. RPC (с 1970-х) с location transparency «фундаментально flawed»: сеть непредсказуема — ответ может потеряться, timeout значит «неизвестно, дошло ли», retry плодит дубликаты (нужна idempotence/deduplication), латентность дико вариабельна, параметры надо кодировать, у языков разные типы (снова 2^53). EJB/RMI, DCOM, CORBA, SOAP/WS-* — всё то же наследие. Привлекательность REST в том, что он не притворяется, будто сеть — это локальный вызов.

Load balancing и service discovery: hardware/software LB (NGINX, HAProxy); DNS — просто, но кеширует протухшие адреса; service discovery (etcd, ZooKeeper) — реестр, heartbeat, метаданные для умного балансирования; service mesh (sidecar-прокси, Istio, Linkerd) — TLS и observability на уровне прокси.

Эволюция RPC: разумно считать, что серверы обновляются раньше клиентов → backward только на requests, forward только на responses. gRPC и Avro RPC наследуют правила своих кодировок; в REST добавление опциональных параметров и новых полей ответа обычно совместимо. Через границы организаций совместимость держат «вечно»: клиентов не заставишь обновляться — приходится параллельно держать несколько версий API; единого способа versioning нет (номер в URL, Accept header, версия, привязанная к API-ключу клиента).

**Durable execution** и workflows: цепочка шагов (task; у Temporal — activity, у Azure — durable functions), которую гоняет workflow engine (orchestrator планирует, executor выполняет). Airflow/Dagster/Prefect — ETL-оркестрация; Camunda/Orkes — BPMN для не-инженеров; Temporal/Restate — durable execution. Мотив: платёж через несколько сервисов нельзя обернуть в транзакцию БД. Durable execution даёт exactly-once: все RPC и изменения состояния пишутся в durable storage (как write-ahead log), при повторе упавшей задачи успешные вызовы не повторяются, а возвращаются сохранённые результаты. Цена: внешние API обязаны быть идемпотентными (уникальные ID); повторное исполнение проигрывает вызовы в прежнем порядке — правка кода хрупка (безопаснее новую версию для новых запусков, старую для доигрывания старых); код должен быть детерминированным — ни random, ни системных часов (фреймворки дают свои реализации, Temporal Workflow Check ловит нарушения статически).

**Event-driven architectures**: событие (event/message) уходит через **message broker** (queue, middleware), sender не ждёт обработки. Выигрыши: буфер при недоступности получателя, redelivery после падений, не нужен service discovery, fan-out нескольким получателям, логическая развязка. История брокеров: TIBCO, IBM WebSphere, webMethods → RabbitMQ, ActiveMQ, NATS, Redpanda, Kafka → Kinesis, Azure Service Bus, GCP Pub/Sub. Два паттерна: queue (достаётся одному потребителю) и topic (всем подписчикам). Формат брокер не навязывает — это байты; обычно protobuf/Avro/JSON + schema registry для проверки совместимости; AsyncAPI — аналог OpenAPI для сообщений. Сообщения часто удаляются после потребления, но можно хранить вечно (event sourcing); при републикации в другой topic надо сохранять неизвестные поля. **Actor model**: concurrency без потоков — актор с локальным состоянием обрабатывает по одному сообщению, async, доставка не гарантирована; в Akka, Orleans, Erlang/OTP location transparency честнее, чем в RPC: потеря сообщений уже заложена в модель. При rolling upgrade совместимость нужна и здесь.

Summary: языковые кодировки заперты в одном языке и часто без forward/backward совместимости; текстовые JSON/XML/CSV распространены, но совместимость зависит от дисциплины использования, а типы (числа, бинарные строки) размыты; бинарные schema-driven (protobuf, Avro) компактны, с чёткими правилами совместимости, схема документирует и генерит код — минус: данные нечитаемы человеком до decode. Потоки данных: БД (writer кодирует, reader декодирует), RPC/REST (клиент↔сервер), события (брокеры и акторы). Вывод: при аккуратности backward/forward compatibility и rolling upgrades вполне достижимы — эволюционируйте быстро, деплойте часто.
