# Глава 3. Data Models and Query Languages

- **PDF:** 89–138 (печать 65–114)
- **Якоря:** declarative query languages, impedance mismatch, ORM, document model, normalization, schema-on-read, schema-on-write, data locality, star schema, property graph, Cypher, recursive CTE, triple store, SPARQL, Datalog, GraphQL, Event Sourcing, CQRS, materialized view, DataFrame

Data model — едва ли не самая важная часть разработки: он определяет не только код, но и то, как мы думаем о задаче. Приложения — это слои data model'ей друг над другом: объекты/структуры в коде → общий data model (JSON/XML, таблицы, граф) → представление в байтах в памяти/на диске/в сети (движок БД, гл. 4) → железо. Каждый слой прячет сложность нижнего за чистым data model. Глава сравнивает relational, document, graph-модели, Event Sourcing и DataFrames плюс их языки запросов: одни данные и запросы удобны в одной модели и неловки в другой.

**Declarative query languages** (SQL, Cypher, SPARQL, Datalog): указываешь *паттерн* данных и преобразования (sort, group, aggregate), но не то, как их достичь — query optimizer сам выбирает индексы, join-алгоритмы и порядок выполнения. Это короче императивного алгоритма, прячет детали движка (БД можно ускорять, не меняя запросы) и позволяет БД распараллелить запрос без усилий разработчика.

**Relational model** (Codd, 1970): данные — relations (tables) как неупорядоченные наборы tuples (rows). Победил network- и hierarchical-модели, пережил object databases и XML databases; в 2010-х его атаковали NoSQL (новые модели, schema flexibility, масштабируемость, open source) и NewSQL (масштабируемость NoSQL + реляционные гарантии) — термины угасли, идеи впитались. Главный след NoSQL — document model: JSON-документы (MongoDB, Couchbase), гибче «жёсткой» реляционной схемы.

**Impedance mismatch** — разрыв между объектами в коде и таблицами/строками/колонками. ORM (ActiveRecord, Hibernate) сокращают boilerplate перевода, но: не могут скрыть разницу моделей; в основном только для relational OLTP (аналитикам всё равно нужна схема); плохая поддержка в экзотических системах; авто-генерация схем бывает неудобной и медленной; легко случайно написать неэффективные запросы — классика **N+1 query problem** (N комментариев + N отдельных lookup'ов авторов вместо одного join). Плюсы ORM: меньше boilerplate, кеширование запросов, помощь с миграциями схемы.

**Document model**: one-to-many (one-to-few) отношения в виде дерева внутри одного JSON-документа (резюме: positions, education, contact_info вложены) — ближе к объектной структуре кода и с лучшей locality: профиль читается одним запросом вместо multiway join по таблицам (shredding документа по таблицам даёт громоздкую схему). Но если связанных записей действительно много (тысячи комментариев) — встраивать всё в документ неуклюже, реляционное представление лучше.

**Normalization vs denormalization**: хранить ID (region_id) или человеко-читаемую строку. Нормализация: осмысленная информация в одном месте, ссылки по ID, который бессмыслен для человека и потому никогда не меняется; обновлять легко, но для показа нужен join. Денормализация: дублирование = больше кода, записей, диска и риск рассинхрона. Правило: normalized быстрее пишется (одна копия), медленнее читается (join'ы); denormalized — наоборот; денормализация — форма derived data, требует процесса обновления копий (atomic transactions или stream processing). Normalized лучше для OLTP; в analytics денормализация безопаснее (bulk-записи, читают в основном). Кейс X/Twitter: materialized timeline хранит только post_id, sender_id и мелочь, а не текст — при чтении идёт hydrating the IDs (резолв по ID в коде приложения, по сути join); это отлично параллелится, так что join'ы при чтении — не препятствие масштабируемости. Что денормализовать — зависит от частоты изменений и стоимости read/write, включая outliers (celebrity users).

**Many-to-many**: в document model — ссылки по ID (org_id в positions); запросы «в обе стороны» — либо дублированные ссылки на обеих сторонах (денормализованно), либо нормализация + secondary indexes по обоим колонкам. Канон реляционного мира — join table (associative table).

**Star schema / snowflake schema** (data warehouse): в центре fact table — событие (покупка, page view), атрибуты + foreign keys в dimension tables (who/what/where/when/how/why; даже даты — dimension с праздниками). Snowflake разбивает dimensions на subdimensions (нормализованнее, но star проще аналитикам). OBT (one big table) — dimensions свёрнуты в денормализованные колонки fact table (предвычисленный join, быстрее запросы, больше места). В analytics денормализация не страшна: это исторический лог, который почти не меняется.

Когда что: document-like дерево, грузящееся целиком → document model; relational лучше для join'ов, many-to-one/many-to-many и прямых ссылок на вложенные элементы (в документе не сослаться на «2-й элемент positions»). Переупорядочиваемые списки (drag-and-drop): JSON array — естественно; в SQL — трюки (integer-колонка с перенумерацией, linked list ID, fractional indexing).

**Schema flexibility**: document DB «schemaless» — миф: есть implicit schema в читающем коде. **Schema-on-read** (структура интерпретируется при чтении) vs **schema-on-write** (БД проверяет при записи) — как dynamic vs static typing, вечный спор. Миграция name → first_name: в document DB — новые поля + код для старых документов; в SQL — ALTER TABLE ADD COLUMN быстр, но UPDATE по всей таблице медленный (инструменты: pt-online-schema-change, gh-ost, pg-osc). Schema-on-read хорош для гетерогенных данных и структур, диктуемых внешними системами.

**Data locality**: документ хранится одной непрерывной строкой (JSON/XML/BSON) — выигрыш, если нужен весь документ; иначе БД грузит лишнее, и каждое обновление переписывает документ целиком → держать документы небольшими, избегать частых мелких апдейтов. Locality достижима и в реляционном мире: Spanner interleaved tables, Oracle multi-table index cluster tables, column families в Bigtable/HBase. Языки документов: от key-value по primary key до secondary indexes и rich языков; XML: XPath/XQuery; JSON: JSON Pointer/JSONPath; MongoDB aggregation pipeline ($match, $group, $lookup — join) — выразительностью подмножество SQL, но в JSON-синтаксисе. **Convergence**: relational добавили JSON и индексы по полям документов, document DB — join'ы, secondary indexes, декларативные языки; гибриды — мощная комбинация (ещё Codd допускал nonsimple domains — вложенные relations).

**Graph data models**: когда many-to-many повсюду. Vertices (nodes/entities) + edges (relationships/arcs): social graph, web graph (PageRank), дорожные сети. Представления: adjacency list (для traversals) vs adjacency matrix (для ML). Гетерогенные графы: Facebook, knowledge graphs (Wikidata). Две модели: property graph (Neo4j, Memgraph, KùzuDB) и triple store (Datomic, AllegroGraph, Blazegraph); Amazon Neptune поддерживает обе.

**Property graph**: vertex = уникальный ID + label + входящие/исходящие edges + properties; edge = ID + tail vertex + head vertex + label + properties. Реализуется двумя реляционными таблицами vertices/edges (properties как jsonb, индексы по head/tail). Никакая схема не ограничивает связи; traversal эффективен в обе стороны; labels позволяют хранить в одном графе разнородные данные; edges — обобщение join table. Ограничение: ребро соединяет лишь две вершины (higher-degree связи — через дополнительную вершину или hypergraph). Графы гибки для evolvability: новые факты — новые вершины/рёбра.

**Cypher** (Neo4j → openCypher; GQL ISO-стандарт 2024 построен на нём): декларативный pattern matching стрелками `(person)-[:BORN_IN]->()`, variable-length traversal `:WITHIN*0..` («ноль или более рёбер», как `*` в regex). Один запрос можно выполнять по-разному (сканировать людей или идти от вершин-локаций по входящим рёбрам) — выбор оптимизатора. В SQL число join'ов при traversal заранее неизвестно — нужны **recursive common table expressions** (WITH RECURSIVE): 4 строки Cypher против 31 строки SQL. Альтернативы: GSQL (TigerGraph), PGQL, Oracle hierarchical queries.

**Triple store**: всё — (subject, predicate, object). Object-примитив → predicate = ключ свойства; object-вершина → predicate = ребро. Варианты: quads (Neptune, +graph ID), Datomic — 5-tuples (+transaction ID и флаг удаления). Turtle — компактный синтаксис (подмножество N3). Корни — Semantic Web (machine-readable данные в интернете): замысел не взлетел, но наследие — JSON-LD, Open Graph, Schema.org, Wikidata, биомедицинские онтологии. **RDF** — модель данных; subject/predicate/object часто URI — глобальные namespace'ы, чтобы чужой `within` не конфликтовал с вашим. **SPARQL** (recursive acronym, «sparkle»): `?person :bornIn / :within* :name "United States"` — паттерны как в Cypher (Cypher заимствовал их у SPARQL), свойства и рёбра в одном синтаксисе.

**Datalog** (1980-е, академия; Datomic, LogicBlox, CozoDB, LinkedIn LIquid): данные — facts (строки таблиц, `born_in(100, 3)`); запрос — набор **rules**: слева от `:-` выводимая виртуальная таблица (как view), справа — паттерны; правила ссылаются друг на друга и рекурсивно на себя — traversal через рекурсию правил (within_recursive). Стиль «шаг за шагом», как функции, вызывающие друг друга; подмножество Prolog; рекурсивные запросы по графам — его сильная сторона.

**GraphQL**: намеренно ограниченный язык для OLTP-запросов клиентских приложений: клиент просит JSON-документ заданной структуры, ответ зеркалит запрос ровно с запрошенными полями — UI меняется без правки серверного API. Ограничения осознанные (запросы от untrusted клиентов): нет рекурсии, нет произвольного поиска — иначе DoS; нужны tooling, авторизация, rate limiting. Реализуется поверх любой БД: сервер хранит нормализованно и выполняет join'ы, объявленные в GraphQL-схеме.

**Event Sourcing / CQRS**: если одну форму данных трудно приспособить ко всем чтениям — пиши в write-optimized форме, а read-optimized представления выводи (derived data). Event log: append-only последовательность self-contained immutable событий с timestamp; события не меняются и не удаляются, только добавляются (новые события могут отменять старые). **Event Sourcing** — события как source of truth, каждое изменение состояния — событие; **CQRS** — разделение write- и read-оптимизированных представлений (термины из DDD; родня — state machine replication). Command → валидация → fact → событие в лог; в логе только валидные события, потребитель не вправе отвергнуть событие; события именуются в past tense («seats were booked»). Отличия от fact table: разные типы событий с разными свойствами (а не единые колонки) и важен порядок событий. Плюсы: события передают intent («бронь отменена» яснее набора UPDATE/DELETE); views пересчитываются из лога воспроизводимо (удалил — пересчитал, починил баг — пересчитал новым кодом); много **materialized views** (projections/read models) под разные запросы, любой data model, денормализация, можно только в памяти; легко добавить новое view и эволюционировать (новые типы событий, старые не трогаем); ошибочное событие отменяется событием-удалением → меньше необратимых действий; лог как audit log; выше write throughput (последовательная запись), лог амортизирует всплески, views догоняют в своём темпе. Минусы: внешние данные ломают детерминизм (курс валюты — клади в событие или бери исторический курс); immutability vs GDPR (удаление per-user лога или crypto-shredding); side effects при reprocessing (не пересылать письма). Реализации: EventStoreDB, MartenDB, Axon Framework; Kafka + stream processors (гл. 12); ключевое требование — все views обрабатывают события ровно в одном порядке.

**DataFrames** (R, Pandas, Spark, ArcticDB, Dask): похожи на таблицу/spreadsheet, но с bulk-операциями в реляционном духе (map по строкам, filter, group by + aggregate, join = merge); управляются последовательностью команд, а не декларативным SQL — под пошаговый «wrangling» данных на локальной копии data scientist'а. Частое применение: pivot реляционных данных в матрицу/многомерный массив (users × movies ratings; sparse matrix с тысячами колонок не поместилась бы в реляционной БД; NumPy sparse arrays). Матрица — только числа: даты масштабируются во float, категории — **one-hot encoding** (колонка на значение, 1/0, обобщается на несколько жанров). Матрицы → linear algebra → большинство ML-алгоритмов (пример — рекомендации фильмов). Array databases (TileDB) — многомерные массивы для науки (геопространственные растры, медицина, телескопы); DataFrames — time series в финансах; пришли в Spark/Flink (гл. 11).

Summary: relational жив и царит в warehousing/analytics (star/snowflake + SQL); document — для self-contained JSON-документов с редкими связями; graph — «всё связано со всем», multi-hop traversal через recursive queries (Cypher/SPARQL/Datalog); DataFrames — мост от реляционных данных к массивам для ML/статистики/науки. Одну модель можно эмулировать другой, но неловко (recursive SQL). Тренд: спец-БД на модель + экспансия в соседние ниши (JSON в relational, join'ы в document, графы в SQL/GQL). Event Sourcing = append-only log + CQRS-views. Общее у nonrelational моделей — нет enforced schema: вопрос лишь в том, explicit она (on write) или implicit (on read). За кадром: genome search (GenBank), double-entry ledgers (TigerBeetle), distributed ledgers/blockchains, full-text search как data model (гл. 4).
