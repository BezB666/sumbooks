# Глава 1. Trade-Offs in Data Systems Architecture

- **PDF:** 25–56 (печать 1–32)
- **Якоря:** data-intensive, OLTP, OLAP, data warehouse, data lake, ETL, ELT, HTAP, system of record, derived data, cloud native, storage-compute disaggregation, multitenancy, vendor lock-in, microservices, serverless, observability, data residency, data minimization

Эпиграф (Thomas Sowell): «Решений нет — есть только trade-off'ы». Глава задаёт рамку всей книги: на архитектурные вопросы нет одного правильного ответа, есть варианты с плюсами и минусами; задача инженера — научиться задавать правильные вопросы и выбирать осознанно.

Приложение называют **data-intensive**, если управление данными — одна из главных сложностей его разработки (в отличие от compute-intensive, где сложность в распараллеливании вычислений). Малые данные на одной машине просты; рост объёма и частоты запросов вынуждает распределять данные по машинам и комбинировать несколько систем. Типовые кирпичи: databases, caches, search indexes, stream processing, batch processing; приложение склеивает их кодом и само выбирает trade-off'ы.

Терминология: **frontend** — код в браузере или мобильном приложении, **backend** — серверный код, обслуживающий запросы. Backend обычно stateless (забывает всё между HTTP-запросами), поэтому состояние живёт либо на клиенте, либо в server-side data infrastructure (БД, кеши, очереди).

**OLTP vs OLAP** — центральное различие главы. Operational systems (OLTP) создают данные: point queries по ключу, низколатентные чтения-записи, вставка/обновление/удаление отдельных записей, фиксированные запросы в коде приложения, данные — «последнее состояние», объёмы от гигабайтов до терабайтов. Analytical systems (OLAP) их читают: агрегаты по огромному числу записей, bulk import (ETL) или event stream, произвольные ad-hoc запросы аналитиков, данные — история событий, терабайты–петабайты. Пользователям OLTP не дают произвольный SQL — это риск для прав доступа и производительности; аналитики в OLAP пишут SQL руками или через BI-инструменты (Tableau, Looker, Power BI).

Отдельный класс — **product analytics / real-time analytics** (Pinot, Druid, ClickHouse): ingest в реальном времени и оптимизация под низкую задержку ответа, тогда как традиционный OLAP загружает данные батчами и оптимизирован под throughput.

**Data warehouse** — отдельная БД для аналитики; тренд разделения возник в конце 1980-х – начале 1990-х. Прямые запросы аналитиков к OLTP-системам плохи: данные размазаны по десяткам-сотням систем (**data silos**), OLTP-схемы неудобны для аналитики, дорогие запросы деградируют производительность для пользователей, сеть OLTP может быть закрыта из соображений безопасности/комплаенса. Warehouse хранит read-only копию данных всех OLTP-систем; данные попадают в него через **ETL** (extract–transform–load), при перемене порядка шагов — **ELT**. Для внешних SaaS (CRM, email-маркетинг, платёжные системы), где исходная БД доступна только через API, ETL делают коннекторы Fivetran, Singer, Airbyte. **HTAP** (hybrid transactional/analytical processing) пытается совместить OLTP и аналитику в одной системе без ETL, но внутри часто скрывает OLTP + отдельную аналитическую систему за общим интерфейсом.

HTAP не заменяет warehouse, а полезен, когда одному приложению нужно и сканировать много строк, и обновлять записи с низкой задержкой (например, fraud detection). Общий тренд: с ростом масштаба системы специализируются под конкретные workload'ы.

**Data lake** — централизованное хранилище файлов без навязанного формата, модели и схемы (Avro, Parquet, текст, изображения, видео, feature vectors…); обычно дешевле реляционного хранилища — живёт на object storage. Появился потому, что data science плохо ложится на SQL-warehouse: нужны **feature engineering** (превращение строк в векторы/матрицы), NLP, computer vision; data scientist'ы предпочитают Pandas, scikit-learn, R, Spark. ETL обобщается до data pipelines, lake становится промежуточной станцией перед warehouse; **sushi principle** — «raw data is better»: каждый потребитель трансформирует сырьё под себя.

Вокруг аналитики выросли практики DataOps (governance, privacy, GDPR/CCPA); аналитика всё чаще потребляет event streams (реакция за секунды вместо суток), а результаты возвращаются в операционные системы через **reverse ETL**: ML-модель, обученная в аналитике, разворачивается в проде (TFX, Kubeflow, MLflow).

**System of record** (source of truth) хранит каноническую версию данных: новые данные пишутся сначала сюда, каждый факт представлен ровно один раз, при расхождении истина здесь. **Derived data** — результат трансформации существующих данных; его можно потерять и пересоздать из источника: кеши, индексы, materialized views, денормализованные значения, обученные модели. Derived data технически избыточна, но часто необходима для производительности чтения. Аналитические системы — обычно derived; операционные — смесь того и другого. Различие зависит не от инструмента, а от того, как он используется в приложении: ясность в том, какие данные из чего выведены, проясняет запутанную архитектуру. Слабое место: при изменении system of record нужно обновлять derived-данные, а БД проектируются в расчёте «одна база на всё»; data pipelines (глава 11) — способ интеграции нескольких систем.

**Cloud vs self-hosting** — вопрос build or buy и бизнес-приоритетов: core competency и конкурентное преимущество делаем сами, рутину отдаём вендору (никто не производит свои CPU). Спектр: своё bespoke ПО → self-hosted off-the-shelf (open source или коммерческое, например MySQL на своей машине) на on-premises железе или на VM в облаке (**IaaS**) → управляемый SaaS через API. Облако — это аутсорсинг эксплуатации. Плюсы: не нужно уметь разворачивать систему и нанимать штат; экспертиза провайдера, накопленная на многих клиентах; главный козырь — переменная нагрузка: можно масштабироваться вверх/вниз и не платить за простаивающие машины (интерактивные аналитические запросы — классический пример пиков). Self-hosting часто дешевле, если команда опытная и нагрузка предсказуемая. Минусы облака — потеря контроля: нет фичи — можно только попросить; сервис лёг — только ждать; нет доступа к метрикам и логам для диагностики; вендор может закрыть сервис или поднять цены — без стандартных API это **vendor lock-in**; санкции могут отрезать доступ; провайдеру приходится доверять безопасность данных.

Популярен гибрид; облако не съест всё: legacy-системы и задачи с особыми требованиями (high-frequency trading требует полного контроля над железом) остаются in-house.

**Cloud native** — архитектура, спроектированная под облачные сервисы с нуля: лучше производительность на том же железе, быстрее восстановление после сбоев, быстрое масштабирование, поддержка больших датасетов (Aurora, Azure SQL Hyperscale, Spanner; Snowflake, BigQuery, Synapse — против MySQL/PostgreSQL/MongoDB и Teradata/ClickHouse/Spark). Ключевая идея — layering сервисов: object storage (S3, Azure Blob Storage, Cloudflare R2) даёт ограниченный API, но скрывает машины, сам распределяет данные и переживает отказы дисков; Snowflake хранит данные в S3, поверх Snowflake строятся другие сервисы. Правило абстракций: задача совпадает с назначением высокоуровневого сервиса — бери его; нет — собирай из низкоуровневых кирпичей.

**Storage-compute disaggregation** — разделение хранения и вычислений. Классика: диск на той же машине, **RAID** — копии на нескольких дисках для переживания отказа. В облаке локальные диски инстансов — скорее эфемерный кеш: диск недоступен, если инстанс упал или заменён на другой размер. Виртуальные диски (EBS, Azure managed disks) эмулируют block device (блоки по 4 KiB) и позволяют гонять legacy-ПО, но каждый I/O — сетевой вызов со своими накладными и чувствительностью к сети.

Cloud native избегает виртуальных дисков и кладёт крупные блоки данных в object storage: например, S3 только хранит, а аналитика выполняется отдельно — данные приходится гонять по сети. **Multitenancy** — данные и вычисления многих клиентов на одном общем железе: лучше утилизация, проще масштабирование и управление для провайдера, но нужна тщательная изоляция, чтобы один клиент не портил производительность и безопасность других.

**DevOps/SRE** пришли на смену DBA/sysadmin: общая ответственность разработки и эксплуатации (SRE — реализация идеи в Google). Философия: автоматизация и повторяемые процессы вместо ручных разовых работ, эфемерные VM вместо долгоживущих серверов, частые обновления, обучение на инцидентах, сохранение знаний организации при смене людей. Облако меняет роль ops: capacity planning превращается в financial planning, оптимизация производительности — в cost optimization; нужно знать лимиты и квоты сервисов, выбирать и интегрировать сервисы, мигрировать между ними — стандартов интеграции пока нет, много ручной работы. Ops не исчезает: безопасность приложения и библиотек, взаимодействие своих сервисов, мониторинг нагрузки, разбор деградаций и аварий остаются на клиенте.

**Distributed vs single-node.** Distributed system — несколько машин-узлов, связанных сетью. Причины распределяться: inherent distribution (клиенты на своих устройствах); запросы между облачными сервисами; fault tolerance/high availability через избыточность; scalability сверх одной машины; latency — серверы в регионах ближе к пользователям; elasticity — платить только за активно используемые ресурсы; specialized hardware (дисковые машины для object store, CPU/память для аналитики, GPU для ML); legal compliance — законы о **data residency** требуют хранить данные граждан в их стране; sustainability — запуск джобов там и тогда, где есть дешёвая возобновляемая энергия. Минусы: любой сетевой вызов может не дойти — сеть рвётся, сервис перегружен или упал, запрос истекает по таймауту, и неизвестно, дошёл ли он, — повторять небезопасно (глава 9); сетевой вызов на порядки медленнее вызова функции в процессе; при больших данных выгоднее принести вычисление к данным, а не наоборот; однопоточная программа на одной машине может быть быстрее кластера на 100+ CPU-ядрах.

Диагностика трудна — нужна **observability** (сбор и запрос данных о выполнении системы: метрики и отдельные события; инструменты OpenTelemetry, Zipkin, Jaeger). Согласованность между сервисами с собственными БД становится проблемой приложения; distributed transactions идут вразрез с независимостью сервисов и редко поддерживаются. Одна машина часто проще и дешевле: с современными CPU/памятью/дисками и однострочными БД (DuckDB, SQLite, KùzuDB) многие нагрузки живут на одном узле.

**Microservices** — эволюция SOA: сервис с одной чёткой целью (S3 — хранение файлов), API для клиентов, одна команда на сервис. Плюсы: независимые обновления и меньше координации, ресурсы под нужды сервиса, смена реализации за API без влияния на клиентов. Обычно у каждого сервиса своя БД: общая БД сделала бы её схему частью API и позволила бы запросам одного сервиса портить производительность другого. Минусы: сложно тестировать (нужно поднимать зависимости), инфраструктура на каждый сервис (деплой, логи, мониторинг, алерты — отсюда Kubernetes), эволюция API ломает клиентов, и часто это вскрывается лишь на staging/production — помогают OpenAPI и gRPC. Микросервисы — техническое решение «людской» проблемы независимости команд: ценны в большой компании, в маленькой — лишний overhead.

**Serverless / FaaS** — аутсорсинг инфраструктуры: провайдер сам выделяет и освобождает ресурсы по входящим запросам, оплата только за время исполнения кода — как metered billing заменил закупку дисков. Ограничения: лимит времени исполнения, ограниченные рантаймы, cold start'ы. Термин обманчив: сервер есть, просто каждый запуск может оказаться на другом; BigQuery и Kafka-сервисы используют «serverless» как синоним autoscaling + оплаты по использованию.

**Cloud computing vs supercomputing (HPC).** Разные приоритеты: суперкомпьютеры — для вычислительно-интенсивной науки (прогноз погоды, климат, молекулярная динамика, оптимизация, PDE), облако — для онлайн-сервисов и бизнес-данных с high availability. HPC: большие batch jobs с checkpoint'ами на диск — при отказе узла кластер останавливают, чинят узел и перезапускают с чекпоинта; облаку останавливаться нельзя. HPC-узлы общаются через shared memory и RDMA (высокий bandwidth, низкая задержка, но предполагается доверие между пользователями); в облаке соседи друг другу не доверяют — нужны изоляция (VM), шифрование, аутентификация. Сети облака — IP/Ethernet с Clos-топологиями ради высокого bisection bandwidth; у суперкомпьютеров — специализированные mesh/torus-топологии под известные паттерны коммуникации. Облако разносит узлы по регионам, HPC предполагает близость узлов. Крупные аналитические системы иногда похожи на HPC.

**Закон, этика, общество.** Инженеры ответственны не только перед бизнесом. С 2018 **GDPR** даёт жителям Европы права на персональные данные (включая право на удаление — right to be forgotten), аналоги — CCPA, для ИИ — EU AI Act. Автоматизированные решения (кредиты, страховки, найм, подозрения в преступлениях) влияют на судьбы людей; соцсети влияют на выборы. Технические следствия: как удалить запись из append-only log, который предполагается неизменяемым? Как удалить данные, вшитые в derived datasets (например, обучающие выборки ML-моделей)? GDPR намеренно не предписывает технологии — только принципы, открытые для интерпретации.

У хранения есть скрытые издержки: репутация и штрафы при утечке, принуждение государств выдать данные; данные о криминализуемых действиях (гомосексуальность в ряде стран, аборты в ряде штатов США) создают реальные риски для пользователей — location data или логи IP-адресов легко выдают такие поездки. Принцип **data minimization** (Datensparsamkeit) противоречит философии «big data» — копить впрок — но соответствует GDPR: цель сбора должна быть явной, использование — только для неё, хранение — не дольше необходимого. Индустрия сама вводит стандарты: PCI для платёжного процессинга, SOC 2 для вендоров — с аудитами третьей стороной.

**Summary.** Тема главы — понимание trade-off'ов: у многих вопросов нет одного верного ответа, есть варианты с плюсами и минусами. Разведены operational (OLTP) и analytical (OLAP) системы — разные данные, паттерны доступа и аудитории; познакомились с data warehouse и data lake, питаемыми через ETL. Сравнили облако с self-hosting: что выгоднее, зависит от ситуации, но cloud native заметно меняет архитектуру — например, разделение storage и compute. Облачные системы распределены по своей природе; распределяться иногда неизбежно, но не стоит спешить, если хватает одной машины. Архитектура определяется не только бизнесом, но и privacy-регулированием, защищающим права людей; как переводить юридические требования в технические решения, пока не формализовано — важно держать это в голове по всей книге.
