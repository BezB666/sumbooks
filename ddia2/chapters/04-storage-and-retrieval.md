# Глава 4. Storage and Retrieval

- **PDF:** 139–184 (печать 115–160)
- **Якоря:** OLTP vs OLAP, log-structured storage, hash index, SSTables, LSM-trees, memtable, Bloom filters, compaction strategies, B-trees, WAL, write amplification, clustered index, covering index, in-memory databases, column-oriented storage, bitmap encoding, vectorization, data cubes, inverted index, vector embeddings

На фундаментальном уровне БД делает две вещи: сохраняет данные и возвращает их по запросу. Глава смотрит на это изнутри БД: как устроены storage engines под транзакционные нагрузки (**OLTP** — много мелких запросов по ключу) и под аналитику (**OLAP** — сложные запросы, сканирующие миллионы записей), плюс индексы для продвинутых запросов. Эпиграф — Фейнман: компьютер «в первую очередь filing system».

**Log и trade-off индексов.** Простейшая БД — две bash-функции: `db_set` дописывает `key,value` в конец файла, `db_get` делает grep и берёт последнее вхождение (`tail -n 1`). Append в конец файла — самая эффективная запись, поэтому **log** (append-only последовательность записей, не путать с application logs) лежит в основе многих БД. Но чтение — O(n): каждый lookup сканирует весь файл. Нужен **index** — производная структура, ускоряющая чтение. Центральный trade-off главы: хорошо выбранные индексы ускоряют чтение, но каждый индекс ест дисковое место и замедляет записи (его надо обновлять при каждой записи) — поэтому БД не индексируют всё по умолчанию, индекс выбирают вручную под типичные запросы приложения.

**Log-structured storage и hash index.** Вариант «append-only файл + индекс»: в памяти hash map key → byte offset последнего значения; lookup = один seek по смещению (если данные в filesystem cache — вообще без дискового I/O). Проблемы: место старых записей не освобождается (файл растёт вечно); hash map не персистентна — при рестарте её перестраивают сканированием всего файла; она обязана помещаться в память (on-disk hash map непрактичен из-за random access I/O и коллизий); нет эффективных range queries (keys 10000–19999 — только по одному ключу). Поэтому на практике данные чаще хранят отсортированными по ключу.

**SSTables** (Sorted Strings Table): пары ключ-значение отсортированы, каждый ключ встречается один раз. Это позволяет **sparse index** — держать в памяти не все ключи, а лишь первые ключи блоков по несколько КБ: находим блок (между handbag и handsome лежит handiwork) и сканируем его. Блоки сжимаются — экономия места и I/O bandwidth ценой CPU. Писать в отсортированный файл на месте нельзя, поэтому используется гибрид log и sorted file: **memtable** (in-memory упорядоченная структура: red–black tree, skip list, trie) принимает записи и по достижении порога (обычно несколько МБ) сбрасывается на диск как новый сегмент-SSTable; старые сегменты периодически сливает фоновая **compaction** — как mergesort: читаем файлы параллельно, копируем меньший ключ, при дублях оставляем свежайшее значение. Чтение: memtable → самый новый сегмент → всё старше, пока ключ не найдётся. Отдельный append-only лог защищает memtable от краха.

**Tombstone и происхождение LSM.** Удаление — это запись-маркер **tombstone**: при merging она заставляет выбросить старые значения ключа; после слияния в самый старый сегмент её можно удалить. Так работают RocksDB, Cassandra, ScyllaDB, HBase; термины SSTable/memtable — из статьи Google Bigtable (2006), сам алгоритм опубликован в 1996 г. как **LSM-tree** (Log-Structured Merge-tree) — отсюда имя LSM storage engines. Сегменты immutable и пишутся за один проход; краш при записи = просто удалить недописанный SSTable (целостность лога проверяют checksums). Сегменты удобно класть в object storage (SlateDB, Delta Lake).

**Bloom filters** — вероятностная проверка «есть ли ключ в этом сегменте»: ключ хешируется в несколько позиций битового массива; хоть один 0 — ключа точно нет (сегмент пропускаем), все 1 — ключ, вероятно, есть (возможен false positive, тогда просто зря прочитали блок). Правило: ~10 бит на ключ дают 1% ложных срабатываний, каждые +5 бит снижают вероятность вдесятеро. Bloom ускоряет point reads по старым/отсутствующим ключам.

**Compaction strategies.** Size-tiered: меньшие SSTables сливаются в большие (например, 4×256 МБ → 898 МБ — не 1024 из-за удалений и TTL); высокая пропускная способность записи, но много временного дискового места. Leveled: SSTables фиксированного размера, разложенные по уровням L0, L1… (выше L0 — key range-разбиение, a–m и n–z); при переполнении уровня часть файлов сливается на уровень ниже; компактнее и лучше для чтения (меньше файлов проверять). Правило: size-tiered — для write-heavy, leveled — для read-dominated нагрузок.

**B-trees.** Самая распространённая структура «чтение-запись по ключу»: придуманы в 1970, через 10 лет уже «ubiquitous»; стандарт почти всех реляционных БД. В отличие от LSM, БД бьётся на страницы фиксированного размера, которые перезаписываются **in place**: традиционно 4 KiB, у PostgreSQL 8 KiB, у MySQL 16 KiB. Страницы ссылаются друг на друга по page number (как указатели, но на диске) и образуют дерево от root; число ссылок в странице — branching factor, на практике несколько сотен. Вставка в заполненную страницу — split на две половинки, каскадом до корня (split корня создаёт новый корень); дерево остаётся сбалансированным, глубина O(log n). Большинство БД помещаются в дерево из 3–4 уровней; 4 уровня по 4 KiB с branching factor 500 вмещают до 250 ТБ.

**WAL.** Перезапись страниц опасна: краш посреди page split даёт осиротевшую страницу, а неатомарная запись страницы — **torn page**. Поэтому каждая B-tree модификация сначала дописывается в **WAL** (write-ahead log, append-only) и лишь затем применяется к страницам; после краха дерево восстанавливается из WAL (в файловых системах аналог — journaling). Страницы буферизуются в памяти; данные durable только после записи в WAL и fsync. Варианты B-tree: copy-on-write (LMDB — изменённая страница пишется в новое место, создаются новые версии родителей; полезно для snapshot isolation, гл. 7); сокращение ключей во внутренних страницах (выше branching factor); последовательная раскладка листьев на диске; ссылки на соседние листья для быстрых сканов.

**B-trees vs LSM-trees.** Правило большого пальца: LSM лучше для write-heavy, B-tree быстрее читает — но бенчмарки чувствительны к нагрузке, надо тестировать своё; бывают и гибриды. Чтение B-tree: одна страница на уровень — быстро и предсказуемо; LSM проверяет несколько сегментов (Bloom помогает point reads, но не range queries — их LSM сканирует по всем сегментам параллельно и сливает). Если memtable не успевает сбрасываться, у LSM возможны latency spikes — RocksDB применяет backpressure, приостанавливая чтение и запись. Записи: B-tree разбрасывает перезаписи страниц по диску (**random writes**), LSM пишет крупные сегменты (**sequential writes**). На HDD разница огромна (позиционирование головки — миллисекунды); на SSD меньше, но есть: flash пишется страницами по 4 KiB, а стирается блоками по 512 KiB, и случайные записи заставляют garbage collector переносить живые страницы — лишние записи и износ.

**Write amplification.** Один write приложения порождает несколько дисковых I/O: в LSM — запись в лог + сброс memtable + каждая compaction; в B-tree — минимум дважды (WAL + страница целиком, даже ради нескольких байт). Коэффициент — суммарные записанные байты / байты «чистого» append-only лога; он съедает пропускную способность диска и изнашивает SSD (у LSM обычно ниже: не пишутся целые страницы, есть сжатие). Бенчмаркить надо долго: на пустой LSM compaction ещё не идёт. По месту: B-tree фрагментируются (в PostgreSQL — vacuum), LSM периодически перезаписывает всё сам и лучше сжимает (leveled экономнее size-tiered); зато удалённые записи в LSM могут жить, пока tombstone не пройдёт все уровни (проблема для compliance), а immutable сегменты дают дешёвые snapshot'ы — в B-tree их снимать сложнее.

**Secondary indexes и хранение значений.** Вторичный индекс — тот же key-value индекс, но значения не уникальны: либо список ID строк (postings list), либо уникальность добавлением row ID. Данные могут храниться: прямо в индексе (**clustered index** — как primary key в InnoDB); как ссылка на **heap file** без порядка (Postgres) или на primary key (вторичные индексы InnoDB); или частично — **covering index** (included columns) отвечает на запрос без обращения к heap, ценой дублирования данных и замедления записей. Обновление значения без смены ключа: если новое ≤ старого — перезапись на месте, иначе перенос в heap и обновление всех индексов или forwarding pointer.

**In-memory databases.** Диски терпели ради durability и дешевизны; с удешевлением RAM многие наборы данных целиком влезают в память. Memcached — чистый кеш; durable in-memory БД добиваются персистентности батарейным RAM, логом на диск, снапшотами или репликацией (VoltDB, SingleStore, Oracle TimesTen, RAMCloud; Redis и Couchbase пишут на диск асинхронно — слабая durability). Контринтуитивно: выигрыш не в отказе от чтения с диска (OS и так кеширует блоки), а в отказе от кодирования in-memory структур в дисковый формат. Бонус — данные, которые трудно держать на диске (priority queues, sets в Redis).

**Аналитика: от warehouse к компонентам.** Data warehouse реляционен — SQL хорошо ложится на аналитику; HTAP-системы (SQL Server, SAP HANA, SingleStore) — фактически два движка за одним SQL-интерфейсом. Cloud warehouses (BigQuery, Redshift, Snowflake) отвязывают вычисления от хранения (object storage) и эластично масштабируются. Open source стек распался на компоненты: query engine (Trino, DataFusion, Presto), storage format (Parquet, ORC, Lance, Nimble), table format (Iceberg, Delta — какие файлы образуют таблицу; time travel, GC, транзакции) и data catalog (Polaris, Unity Catalog — какие таблицы в БД, REST-сервис).

**Column-oriented storage.** В fact-таблицах 100+ колонок, но типичный аналитический запрос читает 4–5 (пример из книги: SUM(quantity) продаж фруктов и конфет по дням недели за 2024 — нужны только date_key, product_sk, quantity). Row-oriented движок грузит с диска все 100+ атрибутов каждой строки. Columnar хранит каждую колонку отдельно, в одинаковом порядке строк: k-й элемент каждой колонки образует k-ю строку. Таблица бьётся на блоки по тысячи/миллионы строк (часто по диапазону timestamp), и запрос читает только нужные колонки нужных блоков. Используется почти всеми: Snowflake, DuckDB, Pinot, Druid, Parquet, ORC, Lance, Nimble, Apache Arrow, Pandas/NumPy, InfluxDB IOx, TimescaleDB. Не путать с wide-column (column-family) моделью Bigtable/Accumulo/HBase — та row-oriented.

**Bitmap encoding.** Компрессия колонок: n различных значений → n битмапов (бит = 1, если в строке это значение); битмапы разрежены, поэтому сжимаются run-length encoding (roaring bitmaps переключают представления). Запросы сводятся к битовым операциям: `product_sk IN (31,68,69)` — OR трёх битмапов, `product_sk=30 AND store_sk=3` — AND двух (k-й бит в разных колонках = одна строка). Работает и для графовых запросов.

**Sort order в column store.** Строки сортируют целиком (не колонки по отдельности), порядок выбирает администратор под типичные запросы: date_key первым ключом — запрос за последний месяц читает только свой диапазон; product_sk вторым — продажи одного товара за день лежат рядом. Сортировка усиливает RLE-сжатие первого ключа (миллиарды строк — в килобайты); второй и третий ключи сжимаются хуже. Запись в columnar: построчно вставлять в середину отсортированной таблицы дорого, поэтому пишут пачками (ETL) — все writes сначала в row-oriented in-memory структуру, затем bulk-слияние с колоночными файлами (Snowflake, Vertica, Pinot, Druid); queries прозрачно читают и диск, и свежие writes из памяти.

**Query execution: compilation vs vectorization.** Оператор-«интерпретатор» слишком медленен для сканов миллионов строк. Два подхода: query compilation — SQL компилируется в машинный код (LLVM), как JIT в JVM; vectorized processing — запрос интерпретируется, но значения обрабатываются батчами готовых операторов (equality-оператор над колонкой возвращает битмап, битмапы комбинируются AND'ом — см. рис. 4-9). Общие приёмы: последовательный доступ к памяти, плотные внутренние циклы без вызовов функций, SIMD и многопоточность, работа прямо над сжатыми данными без декодирования.

**Materialized views и data cubes.** Materialized view — реальная копия результата запроса на диске (в отличие от virtual view — «сокращения» для записи запроса); при изменении данных её надо обновлять (система Materialize). Материализованные агрегаты: **data cube** (OLAP cube) — сетка агрегатов по измерениям: в 2D (date_key × product_sk) каждая ячейка — SUM(net_price), края — итоги по одному измерению; в fact-таблице книги измерений пять (date, product, store, promotion, customer) — принцип тот же. Плюс — предвычисленные запросы мгновенны («продажи по магазинам за вчера»); минус — негибкость: долю продаж товаров дороже $100 не посчитать, цена не измерение. Поэтому хранят сырые данные, а кубы — лишь ускоритель части запросов.

**Multidimensional indexes.** Concatenated index (как бумажный телефонный справочник: lastname, firstname) отвечает только на префиксные запросы — поиск только по first name бесполезен. Геопоиск «рестораны в прямоугольнике карты» (two-dimensional range по latitude и longitude) им не покрыть. Решения: space-filling curve — свернуть координаты в одно число и взять обычный B-tree; специализированные **R-trees** и Bkd-trees (PostGIS строит их поверх GiST в PostgreSQL); регулярные сетки треугольников/квадратов/гексагонов (H3). Многомерность — не только география: (red, green, blue) для поиска цвета товара, (date, temperature) для метеонаблюдений.

**Full-text search.** Каждый терм — измерение: документ содержит слово → 1 в этой размерности. **Inverted index**: терм → список ID документов (**postings list**); при последовательных ID это разреженный битмап, и запрос «red AND apples» — битовый AND двух битмапов. Так работает Lucene (движок Elasticsearch и Solr): терм→postings хранятся в SSTable-подобных отсортированных файлах со слиянием в фоне; у PostgreSQL для этого тип индекса GIN. Альтернатива словам — **n-grams** (триграммы hello: hel, ell, llo): substring-поиск и даже regex, но индекс большой. Опечатки: Lucene ищет слова в пределах edit distance (1 = одна буква добавлена/удалена/заменена), превращая термы в конечный автомат (Levenshtein automaton).

**Vector embeddings.** Semantic search понимает смысл, а не буквы: «cancel subscription» находит страницу «terminate contract». Embedding-модель (часто LLM) переводит текст в вектор float'ов (обычно 1000+ измерений); семантически близкие документы → близкие точки. Расстояние — cosine similarity или Euclidean distance. Ранние модели текстовые (Word2Vec, BERT, GPT), новые мультимодальные (текст+картинки). Векторный индекс ищет ближайших соседей запроса: flat — точный, но сравнивает всё; IVF — кластеризация на partitions (centroids), число проверяемых — probes, больше probes = точнее, но медленнее; HNSW — многослойный граф соседств, спуск от верхнего разреженного слоя. IVF и HNSW приблизительны; реализованы в Faiss и pgvector. (Не путать с vectorized processing — там «вектор» это батч битов для SIMD.)

**Summary (итог главы).** Два типа движков: OLTP — много маленьких запросов по primary/secondary ключу, индексы упорядочены и поддерживают range queries; аналитика — сканы множества записей, columnar layout + сжатие + JIT/vectorization. Две школы OLTP-хранилищ: log-structured (только append и удаление файлов, никогда update in place: SSTables, LSM-trees, RocksDB, Cassandra, HBase, ScyllaDB, Lucene) — высокая пропускная способность записи; update-in-place (B-trees — все крупные реляционные БД) — как правило, быстрее читают. Далее — многомерные индексы (R-trees, геопоиск), full-text (несколько ключевых слов), векторные БД для semantic search. Знание внутренностей помогает выбрать подходящий инструмент, осмысленно крутить параметры настройки и понимать документацию выбранной БД.
