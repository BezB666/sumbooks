# Глава 6. Replication

- **PDF:** 221–274 (печать 197–250)
- **Якоря:** replication, single-leader, replication lag, synchronous vs asynchronous, failover, split brain, logical log, eventual consistency, read-your-writes, monotonic reads, consistent prefix reads, multi-leader, sync engine, local-first, LWW, CRDT, leaderless, quorum, hinted handoff, version vectors

**Replication** — хранить копию одних и тех же данных на нескольких машинах, связанных сетью. Цели: близость данных к пользователям (latency), продолжение работы при отказах частей (availability и durability), масштабирование чтений (read throughput). Вся сложность — в обработке *изменений*: статику достаточно скопировать один раз. Три семейства алгоритмов: single-leader, multi-leader и leaderless — почти все распределённые БД используют одно из них; принципы не менялись с 1970-х, потому что не изменились фундаментальные ограничения сетей. Replication ≠ backups: реплики быстро разносят записи по узлам, бэкапы хранят старые снимки для возврата в прошлое (случайное удаление репликация только размножит).

**Single-leader replication** (leader-based, primary-backup, active/passive): одна реплика — leader (primary, source) — принимает все записи и рассылает их followers (read replicas, secondaries, hot standbys) через replication log / change stream; читать можно с любой реплики, писать — только на лидера. Встроено в PostgreSQL, MySQL, Oracle Data Guard, SQL Server Always On, MongoDB, DynamoDB, Kafka; на Raft работают CockroachDB, TiDB, etcd, RabbitMQ quorum queues. Термин master–slave считается оскорбительным, его избегают.

**Synchronous vs asynchronous replication**: синхронный follower подтверждает запись до того, как лидер сообщает клиенту об успехе — у него гарантированно актуальная копия, но его сбой или зависание блокирует *все* записи. Поэтому обычна схема **semisynchronous**: один follower синхронный, остальные асинхронные; при выпадении синхронного им становится другой — актуальная копия гарантирована минимум на двух узлах.

Вариант — синхронное большинство (3 из 5 — пример quorum), часто с протоколом консенсуса для автоматических выборов лидера. Полностью асинхронная репликация: подтверждённая клиенту запись не обязана быть durable — при гибели лидера неотреплицированные записи теряются; зато лидер продолжает писать, даже если все followers отстали. В норме репликация занимает меньше секунды, но при восстановлении узла, работе на пределе мощности или сетевых проблемах lag вырастает до минут и больше.

**Setting up new followers**: consistent snapshot лидера → копия на новый узел → запрос всех изменений с момента снимка по позиции в логе (PostgreSQL: log sequence number; MySQL: binlog coordinates и GTID) → caught up. Архивация лога и снимков в object store (WAL-G, Litestream) — готовый механизм бэкапов и disaster recovery.

Новое во 2-м издании — БД поверх object storage (S3, GCS, Azure Blob): дёшево, высокая durability, CAS для транзакций и выборов лидера, интеграция через Parquet/Iceberg; минусы — высокие latency, плата за API-вызовы (вынуждает батчить), имммутабельность объектов. Крайний случай — **zero-disk architecture (ZDA)**: все данные в object store, диски и память лишь кеш, узлы без персистентного состояния (WarpStream, Confluent Freight, Bufstream, Redpanda Serverless, облачные data warehouses).

**Отказы узлов**: follower восстанавливается catch-up'ом по своему логу; лидер выбирает — держать лог ради долго отсутствующего follower (риск переполнить диск) или удалить его (follower придётся восстанавливать из бэкапа). **Failover**: определить смерть лидера (обычно timeout, напр. 30 с), выбрать нового (выборы большинством или назначение controller node; кандидат — самый свежий follower), переконфигурировать систему (старый лидер должен стать follower).

Риски failover: потеря неотреплицированных записей; **split brain** — два узла считают себя лидером (защита — **fencing**); неверно выбранный timeout — короткий даёт лишние failover при всплеске нагрузки и лишь усугубляет её. Инцидент GitHub: повысили отставший MySQL-follower, его автоинкрементный счётчик переиспользовал первичные ключи, рассинхрон с Redis → чужие данные показаны не тем пользователям. Главное — выбрать самый свежий follower (синхронный или с наибольшим log sequence number): потеря доли секунды записей терпима, отставание на дни — катастрофа.

**Логи репликации**: statement-based (логировать SQL) — ломается на NOW()/RAND(), автоинкременте, триггерах и хранимках; VoltDB требует строгого детерминизма. **WAL shipping** (PostgreSQL, Oracle) — реплицируются изменения байтов в дисковых блоках: жёсткая связь со storage engine, разные версии ПО на узлах невозможны, апгрейд с даунтаймом.

**Logical (row-based) log** — записи на уровне строк (insert/delete/update + commit), отделён от storage engine: MySQL binlog, логическое декодирование WAL в PostgreSQL. Позволяет zero-downtime upgrade (сначала followers, потом failover) и легко парсится внешними системами — основа **change data capture** (гл. 12).

**Replication lag и eventual consistency**: read-scaling (много followers, чтения с них) реалистичен только при асинхронной репликации — полная синхронность означает, что отказ одного узла останавливает всю систему, а узлов тем больше, чем вероятнее отказ. Чтение с асинхронного follower может вернуть устаревшие данные — это **eventual consistency** (термин Terry et al., популяризован Werner Vogels; свойственна и асинхронным реляционным БД, не только NoSQL). «Eventually» намеренно расплывчато: lag обычно доли секунды, но может стать секундами и минутами.

**Read-your-writes** (read-after-write) — пользователь всегда видит свои записи: читать свой профиль с лидера; минуту после обновления читать с лидера или не пускать запросы на followers, отставшие более чем на минуту; помнить timestamp последней записи клиента и ждать/менять реплику. Сложнее между устройствами и регионами — метаданные надо централизовать, а запросы всех устройств маршрутизировать в один регион.

**Monotonic reads** — не видеть время «вспять» (комментарий появился и исчез): маршрутизировать чтения одного пользователя на одну реплику (hash user ID). **Consistent prefix reads** — каузальный порядок (ответ не раньше вопроса, диалог Poons/Cake): беда sharded БД, где у shard'ов нет общего порядка; лечится записью каузально связанных данных в один shard или трекингом зависимостей. Если lag в минуты/часы ломает UX, честнее взять БД с сильной консистентностью (linearizability + ACID, тренд NewSQL), чем притворяться, что асинхронная репликация синхронна.

**Multi-leader replication** (active/active, bidirectional): несколько лидеров принимают записи, каждый — follower для остальных. Синхронный вариант эквивалентен single-leader (обрыв сети блокирует запись), поэтому рассматривается только асинхронный. Оправдан в **geo-distributed** развёртываниях: запись обрабатывается в локальном регионе (интернет-задержка скрыта от пользователя), регион переживает отказы сети и целого региона автономно; цена — сильно более слабая консистентность: нельзя гарантировать уникальность username или неотрицательный баланс счёта (записи, корректные по отдельности, вместе нарушают инвариант). Поддерживают MySQL, Oracle, SQL Server, YugabyteDB; аддоны: Redis Enterprise, EDB Postgres Distributed, pglogical. Подводные камни: автоинкремент, триггеры, integrity constraints — «dangerous territory».

**Topologies**: circular и star (tree) — один упавший узел разрывает поток репликации между остальными, нужны теги пройденных узлов против бесконечных циклов. All-to-all — нет single point of failure, но сообщения могут «обгонять» друг друга: update приходит раньше своего insert (каузальность нарушена); timestamp'ы не спасают — часы ненадёжны, нужны version vectors, которые многие системы не реализуют.

**Sync engines и local-first**: календари на устройствах — каждое устройство это лидер, асинхронный multi-leader sync с lag в часы и дни; offline = просто очень большая сетевая задержка. Реалтайм-коллаборация (Google Docs, Figma, Linear) — та же архитектура: каждая вкладка браузера = реплика. **Sync engine** — библиотека захвата изменений, отправки и слияния; первопроходец — Lotus Notes (1980-е); современные: Firestore, Realm, Ditto (проприетарные), PouchDB/CouchDB, Automerge, Yjs (open source). Offline-first — редактирование без сети; **local-first** — работает даже если вендор закрыл все онлайн-сервисы (открытый протокол синка; пример — Git). Плюсы: мгновенный UI (ответ в следующем кадре, 16 мс при 60 Hz), нет отдельного offline-режима, декларативное программирование без обработки ошибок RPC. Минус: не годится для огромных наборов данных (весь каталог интернет-магазина не скачаешь).

**Конфликты записей**: две записи **concurrent**, если ни одна не знала о другой в момент записи (wiki-заголовок A→B и A→C у двух лидеров). Способы: **conflict avoidance** — маршрутизировать все записи записи на одного лидера (не работает при смене лидера); чётные/нечётные ID у двух лидеров. **LWW (last write wins)** — побеждает запись с большим timestamp, при равенстве — сравнение значений; «последняя» — обман: порядок конкурентных записей случаен, проигравшие молча выбрасываются (data loss), плюс чувствительность к рассинхрону часов (лечится logical clock).

**Manual resolution** — БД хранит все конкурентные значения (**siblings**), приложение или пользователь сливает их (CouchDB): API усложняется (строка превращается в множество строк), UI merge тяжёл для пользователя, наивный union может «воскресить» удалённое (анекдот про корзину Amazon: удалённые Book и DVD вернулись), а параллельные резолюции порождают новые конфликты (B/C и C/B → B/C/C/B).

**Automatic resolution** — цель: все реплики, обработавшие одно множество записей, сходятся к одному состоянию независимо от порядка = **strong eventual consistency**. Алгоритмы по типам данных: текст (трекинг вставок/удалений), коллекции (помнить удаления — корзина сходится к {Soap}), счётчики (инкременты/декременты суммируются без двойного счёта), key-value maps (по ключам независимо). Предел — инварианты вроде «не больше 5 элементов в списке» автоматически не выразимы.

**CRDT и OT**: два семейства автослияния. Пример: «ice» → prepend n и append ! должны дать nice!. **OT (operational transformation)** оперирует индексами (вставка ! на позицию 3 трансформируется в 4 из-за конкурентной вставки n); **CRDT** даёт каждому символу уникальный неизменяемый ID и вставляет «после ID такого-то», конкурентные вставки упорядочиваются по ID — сходимость без трансформаций. OT — Google Docs; CRDT — Redis Enterprise, Riak, Azure Cosmos DB; JSON sync engines: Automerge, Yjs (CRDT) и ShareDB (OT). Конфликты бывают и неявные: два бронирования одной переговорки — обе записи-вставки корректны по отдельности, но вместе дают пересечение броней.

**Leaderless replication**: любая реплика принимает записи; клиент пишет и читает сразу несколько узлов параллельно (координатор, если есть, не задаёт порядок записей). Leaderless системы были первыми ещё в 1970-х; идею возродил Amazon Dynamo (2007) → **Dynamo-style**: Riak, Cassandra, ScyllaDB (сам DynamoDB при этом single-leader на Multi-Paxos — не путать с Dynamo). Запись, подтверждённая 2 из 3 реплик, считается успешной.

Отставшую реплику догоняют три механизма: **read repair** (клиент видит stale-ответ и перезаписывает свежее значение; хорош для часто читаемых значений), **hinted handoff** (сосед хранит hints за упавший узел и передаёт их при его возвращении) и **anti-entropy** (фоновый процесс сверки, копирует без порядка и со значительной задержкой). Каждое значение несёт version/timestamp, чтобы отличать свежее от устаревшего.

**Quorum**: при n репликах запись подтверждают w узлов, чтение опрашивает r узлов; если **w + r > n**, множества чтения и записи пересекаются — среди прочитанного гарантированно есть свежее значение. Типично n нечётное (3 или 5), w = r = (n+1)/2; n=3, w=2, r=2 терпит один упавший узел, n=5, w=3, r=3 — два. Для read-heavy нагрузок берут w=n, r=1 (быстрые чтения, но один упавший узел блокирует все записи). Quorum не обязан быть большинством — важно лишь пересечение множеств.

Но w+r>n — не железная гарантия: восстановление узла со старой копии, rebalancing, чтение конкурентное записи, неоткаченные частичные записи, часы реального времени (Cassandra/ScyllaDB) — всё это ломает «свежесть»; w и r регулируют лишь *вероятность* stale-чтений, а мониторить staleness в leaderless системах сложно (нет позиции в логе). При w+r≤n — ниже latency и выше доступность, но чаще stale.

**Single-leader vs leaderless по производительности**: у single-leader чтения с лидера ограничены его мощностью, заметны failover и любое замедление лидера. Leaderless устойчивее: нет failover, запросы параллельны, **request hedging** (брать самый быстрый ответ) режет tail latency, а **gray failures** (узел жив, но деградировал и медленно отвечает) не требуют решения «пора ли failover». Минусы leaderless: нагрузка hinted handoff в момент, когда система и так под нагрузкой; большие quorum'ы = ждать больше ответов и выше шанс попасть на медленную реплику (на практике редко больше 4 из 7 или 5 из 9); при массовом обрыве сети — **sloppy quorum** (Riak/Dynamo) или consistency level ANY (Cassandra/ScyllaDB): писать на любые достижимые реплики, без гарантии, что чтение увидит запись.

**Multi-region operation**: в Cassandra/ScyllaDB координатор в локальном регионе шлёт запись местным репликам и по одной в каждый другой регион (экономия cross-region трафика); уровни консистентности — quorum по всем регионам, отдельный quorum в каждом или только локальный (быстрее, но вероятнее stale). В Riak n — реплики внутри одного региона, межрегионная репликация асинхронна в фоне, в стиле multi-leader.

**Happens-before и version vectors**: A happens before B, если B знает о A или зависит от неё; **concurrent** = ни одна не happened before другой. Важно знание, а не совпадение по времени — аналогия с теорией относительности; в компьютерах медленная сеть делает записи в разное время конкурентными. Алгоритм (на одной реплике): сервер хранит version number ключа, инкрементит при каждой записи; чтение возвращает все siblings + версию; клиент обязан читать перед записью и писать с версией и слитыми значениями; сервер затирает значения ≤ указанной версии и хранит более новые (конкурентные). Пример с корзиной: milk (v1); eggs (v2, siblings milk+eggs); [milk, flour] (v3) затирает v1, хранит v2; [eggs, milk, ham] (v4); [milk, flour, eggs, bacon] (v5)… — старые версии со временем затираются, записи не теряются.

На нескольких репликах одной версии мало: нужна версия per replica per key — **version vector** (Riak 2.0: dotted version vectors, «causal context»). Он отличает overwrite от конкурентной записи и позволяет прочитать с одной реплики, а записать на другую без потерь. Version vector ≠ vector clock (тонкое различие).

**Summary**: цели репликации — high availability, durability, disconnected operation, latency, scalability чтений. Три подхода: single-leader (прост в понимании, сильная консистентность, но чтения с followers могут быть stale), multi-leader и leaderless (живучее к отказам узлов, сетевым разрывам и скачкам latency — ценой разрешения конфликтов и более слабых гарантий). Sync vs async кардинально меняет поведение при сбоях: при async после гибели лидера недавно «закоммиченные» данные могут пропасть. Аномалии lag и модели поведения: read-after-write, monotonic reads, consistent prefix reads. Сходимость реплик — через version vectors (детект конкурентности) и алгоритмы слияния: CRDT, LWW или ручное разрешение. Вся глава предполагала, что каждая реплика хранит весь датасет; далее (гл. 7) — sharding, когда данные не помещаются на одну машину.
