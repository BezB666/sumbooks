# Глава 5. Component-Based Decomposition Patterns (Паттерны компонентной декомпозиции)

- **PDF:** 124–231 (печать 112–219)
- **Якоря:** Identify and Size Components (выявить и оценить размер), Gather Common Domain Components (собрать общие доменные), Flatten Components (выровнять), Determine Component Dependencies (зависимости), Create Component Domains (домены компонент), Create Domain Services (доменные сервисы), architecture story (архитектурная история)

Addison и Austen выбрали component-based путь, в интернете почти ничего нет. Logan: паттерны итеративные, цель — безопасно дойти до service-based / микросервисов; «второго раза не будет». Порядок важен: сначала понять и починить компоненты *внутри* монолита, потом группировать, и только потом выносить в отдельные деплои.

**Architecture story** (архитектурная история) — запись рефакторинга ради *структуры*: «мне нужно decouple payment service, чтобы легко добавлять способы оплаты». Это не user story (новая фича) и не tech debt («почистим потом»): это срочное структурное изменение под характеристику (scalability, time-to-market). На каждый шаг вешают **fitness function** (фитнес-функция — проверка в CI/CD, что характеристика не сломалась): oversized-компонент, дубли доменных классов между namespace, слишком много `.sharedcode`.

Шесть паттернов идут строго подряд:

| Pattern | Суть: что делаем и чем это плохо, если пропустить |
|---|---|
| Identify and Size Components (выявить и оценить) | Инвентаризация: переписать все компоненты и измерить каждый в **statements** (не в файлах/строках — все пишут код по-разному). Целевой размер — 1–2 σ от среднего. Слишком крупный компонент «делает слишком много»: сильнее сцеплен, его тяжелее выносить; слишком мелкий «не делает ничего» и дробит зря |
| Gather Common Domain Components (собрать общие доменные) | Схлопнуть дубли *доменной* логики (notification, валидация, форматирование) в один компонент. Infrastructure-код (logging, metrics, security) не трогаем — он и так общий для всех. Иначе при нарезке размножатся почти одинаковые сервисы с едва заметными отличиями |
| Flatten Components (выровнять) | Компонент должен быть листом дерева namespace. Как только внутри `ss.survey` появился `ss.survey.templates`, сам `ss.survey` перестаёт быть компонентом и становится subdomain. Код «посередине дерева» — без собственной идентичности, его нельзя честно вынести отдельным сервисом |
| Determine Component Dependencies (зависимости) | Смотрят сцепление *между компонентами* (afferent CA — кто зависит от него, efferent CE — от кого зависит он), а не месиво внутри класса. Граф отвечает на три вопроса: можно ли резать, сколько усилий, рефакторинг или переписывание. Грубая прикидка усилия — размер мяча: **golfball** (минимум зависимостей → feasible, refactoring), **basketball** (много зависимостей → «maybe», часть кода переписывать), **airliner** (слишком запутано → не режем, это rewrite целиком). Если огромная доля кода — `.sharedcode`, distributed превратится в кошмар из общих библиотек |
| Create Component Domains (домены компонент) | Сгруппировать компоненты в домены: 1 будущий сервис : N компонент. Иерархия namespace `domain.subdomain.component` и есть способ изобразить домен: второй узел — домен, третий — subdomain, лист — компонент |
| Create Domain Services (доменные сервисы) | Вынести готовые домены в отдельно деплоимые **domain services** — крупнозернистые сервисы по одному на домен. Получается service-based: UI + coarse services + пока ещё одна общая БД |

После этого система уже не один монолитный процесс, но данные всё ещё общие. Гранулярность «резать ли Ticketing на четыре сервиса» — гл. 7. Данные — гл. 6.
