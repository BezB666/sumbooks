# Глава 11. Managing Distributed Workflows (Управление распределёнными потоками)

- **PDF:** 505–557 (печать 493–545)
- **Якоря:** orchestration (оркестрация), choreography (хореография), state owner (владелец состояния), ESB

Austen врывается к Logan: «напишу ADR — в новой архитектуре только choreography, так максимально decoupled». Logan: never say never; «всегда» в архитектуре почти не бывает. Это возврат к **dynamic coupling** (гл. 2): как сервисы играют вместе в workflow, не как они сваренны статически.

Два стиля. **Orchestration** (оркестрация): есть медиатор / оркестратор, который знает шаги, ошибки, статус. В микросервисах это **оркестратор на конкретный workflow**, не глобальный **ESB** (enterprise service bus — корпоративная шина «все через центр»). Плюс: сложный поток, recoverability, видно state. Цена: coupling к медиатору, хуже responsiveness / FT / scale (кванты снова связаны через дирижёра).

**Choreography** (хореография): сервисы подписываются на события, центра нет. Плюс: scale, отзывчивость, меньше одной точки. Цена: happy path выглядит просто, а ошибка (товар кончился после оплаты и письма) заставляет каждый сервис слать compensating messages (компенсирующие сообщения) всем, кого уже затронули — граф рёбер раздувается. State всё равно где-то живёт: либо медиатор, либо front controller / «кто последний знал».

Правило главы: сложность workflow и семантика ↑ → нужен оркестратор. Хореография кормит саги Phone Tag / Time Travel / Anthology; оркестрация — Fairy Tale / Fantasy Fiction / Parallel (имена и матрица — гл. 12). Sysops: **ADR — orchestration для primary ticket workflow** (надо трекать статус, ошибки, «где тикет»; риск — scale самого оркестратора).
