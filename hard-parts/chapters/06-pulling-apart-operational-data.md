# Глава 6. Pulling Apart Operational Data (Разделение операционных данных)

- **PDF:** 232–317 (печать 220–305)
- **Якоря:** data disintegrators (дезинтеграторы данных), data integrators (интеграторы данных), data domain (домен данных), ACID, BASE, CAP, polyglot (полиглот)

Доменные сервисы уже деплоятся отдельно, а БД всё ещё одна. Addison зовёт Dana (data architect) и Devon (DBA). Dana: «монолитная БД нормальна, я за неё отвечаю, не трогать». Devon: есть пятишаговый процесс через **data domains** (домены данных), плюс разным данным можно подобрать разные типы БД (knowledge base и survey — не то же, что тикеты). Конфликт «данные vs архитектура» из гл. 1 становится конкретным: пока все сервисы ходят в одну БД, **architecture quantum** (квант = что надо поднять с нуля, чтобы кусок заработал) равен 1, сколько бы процессов ни вынесли.

Резать данные или держать вместе — две силы. Каждый пункт отвечает на вопрос «что случится, если данные останутся общими / если их разрезать».

| **Data disintegrators** (дезинтеграторы — когда резать) | Суть |
|---|---|
| Change control | Схему меняют команды разных сервисов; правка одной ломает чужой сервис. Своя БД = своя схема и свой темп изменений |
| Connection management | У каждого сервиса свой пул коннектов; один выедает все коннекты, другой стоит в очереди (или наоборот — пул простаивает) |
| Scalability | Нельзя масштабировать данные одного сервиса отдельно — растёт вся БД, даже если «горячий» только один домен |
| Fault tolerance | Падение БД или одного сервиса валит всех, кто к ней подключён |
| Architectural quantum | Общая БД склеивает кванты всех сервисов в один — независимый деплой ничего не даёт |
| Database type optimization | Разным данным — разный тип БД: knowledge base (документы/поиск) и survey не обязаны жить в реляционной схеме тикетов |

| **Data integrators** (интеграторы — когда держать вместе) | Суть |
|---|---|
| Data relationships | Связи между таблицами через FK / views / triggers. Резать, не сняв эти связи, — получить скрытый монолит через БД (сервисы начнут ходить друг к другу за чужими данными) |
| ACID transactions | Атомарные транзакции *между* таблицами разных доменов; разрезал — потерял эту гарантию, придётся строить компенсацию |

Пять шагов data domains: 1) анализ и нарезка доменов, 2) разложить таблицы по доменам, 3) отдельные коннекты к схемам (ещё на одном сервере), 4) схемы на свои серверы, 5) switch-over (переключение сервисов на свои БД). Cross-domain FK/views снимают (приём из *Refactoring Databases*). Домен ≠ схема: схема — механизм хранения, домен — смысл (чьи данные и кто их меняет).

Выбор типа БД — paradox of choice (парадокс выбора). Оси сравнения: learning curve (порог входа), scale/throughput (масштаб и пропускная способность), availability / partition tolerance (доступность при разделении сети), consistency (ACID vs BASE / eventual), приоритет чтения или записи. Типы: relational, key-value, document, column family, graph, NewSQL, cloud native, time-series. CAP всплывает рядом с Table Split (гл. 9). Sysops: **ADR — document DB для customer survey** (опрос не обязан жить в той же реляционной схеме, что тикеты).
