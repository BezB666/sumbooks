# Глава 1. What Happens When There Are No “Best Practices”? (Что бывает, когда нет «лучших практик»?)

- **PDF:** 13–45 (печать 1–33)
- **Якоря:** trade-off (компромисс), least worst (наименее плохое), ADR (запись архитектурного решения), fitness function (фитнес-функция), architecture quantum (квант архитектуры), operational data (операционные данные), analytical data (аналитические данные)

Разработчик гуглит конфиг и находит ответ. Архитектор — нет: почти каждая задача смешивает стек, организацию и историю *этой* компании, поэтому это снежинка, а не Stack Overflow. Книги и «best practice» (лучшая практика) появляются, когда кто-то нашёл общее хорошее решение. У архитектуры целые классы задач, где общего хорошего нет: один грязный набор trade-off’ов (компромиссов) против почти такого же грязного. Silver bullet (серебряная пуля) не ищут. Цель — **least worst** (наименее плохой) набор компромиссов, который ещё можно объяснить. Книга про *как решать*, не про конкретный брокер или фреймворк.

Данные живут дольше систем. **Operational data** (операционные / OLTP) — запись заказа, тикета, профиля. **Analytical data** (аналитические) — отчёты, тренды, data science. Их цели, схемы и нагрузка разные; если свалить в одну БД, operational и analytics начинают душить друг друга. Напряжение «данные vs архитектура» — один из источников «hard parts» (трудных частей). Когда БД выносят внутрь границы сервиса (как в микросервисах), транзакционность перестаёт быть «проблемой DBA» и становится архитектурной.

Как фиксируют решения: **ADR** (Architecture Decision Record / запись архитектурного решения) — короткий файл Context / Decision / Consequences (контекст / решение / последствия), чтобы через год было видно *почему*, а не только *что*. Второй закон из *Fundamentals*: why (почему) важнее how (как). Как держат решение в коде: **fitness functions** (фитнес-функции; из Building Evolutionary Architectures) — любой механизм, который объективно проверяет, что характеристика жива (ArchUnit, тесты, линтеры). Atomic (атомарные) проверяют одну вещь; holistic (целостные) — систему целиком. Это исполняемый чеклист важных, но не срочных принципов: без автоматики срочность съедает качество, и «потом починим» не наступает. Не строить ivory tower из сотен функций — только то, без чего архитектура развалится.

Словарь, которым книга пользуется дальше: coupling (сцепление), component (компонент), sync/async (синхронно/асинхронно), orchestration/choreography (оркестрация/хореография), atomicity (атомарность), contract (контракт — любой стык двух кусков ПО). **Architecture quantum** (квант архитектуры) здесь только называется; определение — гл. 2.
