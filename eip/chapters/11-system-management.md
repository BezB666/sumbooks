# Глава 11. System Management (Управление системой)

- **PDF:** стр. 476–503
- **Роль:** прод messaging. Тестировать слабосвязанный асинхронный поток тяжелее, чем писать его. Fowler: architect's dream, developer's nightmare (мечта архитектора, кошмар разработчика).
- **Якоря:** Control Bus (шина управления), Detour (объезд), Wire Tap (прослушка), Message History (история сообщения), Message Store (хранилище сообщений), Smart Proxy (умный прокси), Test Message (тестовое сообщение), Channel Purger (очиститель канала)

Два уровня наблюдения:

- System management (управление системой) — сколько сообщений, сколько шли, header, Message History
- BAM (Business Activity Monitoring / мониторинг бизнес-активности) — payload (сумма заказов за час). Паттерны годятся для обоих; книга держит фокус на system management (BAM ≈ свой мир + data warehouse)

Три блока: контролировать, смотреть трафик, тестировать.

## Monitoring and controlling (мониторинг и управление)

| Паттерн | Зачем |
|---|---|
| Control Bus (шина управления) | отдельные каналы только для управления; консоль видит статус и шлёт команды |
| Detour (объезд) | временно пустить поток через валидацию/лог; выключатель с Control Bus, чтобы не платить за это всегда |

## Observing traffic (наблюдение за трафиком)

| Паттерн | Зачем |
|---|---|
| Wire Tap (прослушка) | копия сообщения в другой канал, основной поток не трогаем (на PTP; на pub/sub можно просто ещё подписчика) |
| Message History (история сообщения) | в самом сообщении список пройденных узлов; без знания «кто консьюмер» у продюсера |
| Message Store (хранилище) | центральный архив всех сообщений; вместе с History можно восстановить граф путей |
| Smart Proxy (умный прокси) | для Request-Reply (запрос-ответ): подменить Return Address (адрес возврата), увидеть и запрос и ответ, померить QoS (гл. 12) |

History привязан к одному сообщению. Store — ко всем. Proxy нужен, потому что reply уезжает на чужой Return Address, Wire Tap на request-канале ответ не поймает.

## Testing and debugging (тестирование и отладка)

| Паттерн | Зачем |
|---|---|
| Test Message (тестовое сообщение) | периодически впрыснуть известный запрос, проверить ответ (не ждать жалоб клиентов) |
| Channel Purger (очиститель канала) | вычистить канал от застрявших (тест, «ядовитое» сообщение, которое валит консьюмера по кругу) |

Транзакции не спасают от программной ошибки «забыли прочитать reply» — сообщение останется. Correlation Identifier (идентификатор корреляции) помогает отличить старый reply. Purger: в тесте снести всё; в проде — выборочно, иногда сохранить и потом replay (повтор; стор + purger).

Пример в книге: простой JMS-purger, `receiveNoWait` в цикле. Связан с Invalid Message Channel (канал неверных), Point-to-Point (точка-точка), Message Store.
