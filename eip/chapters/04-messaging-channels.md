# Глава 4. Messaging Channels (Каналы сообщений)

- **PDF:** стр. 108–139
- **Роль:** какие бывают каналы и как ими соединять чужие системы и чужие брокеры.
- **Якоря:** Point-to-Point (точка-точка), Publish-Subscribe (публикация-подписка), Datatype Channel (канал типа данных), Dead Letter (недоставленное), Invalid Message (неверное сообщение), Guaranteed Delivery (гарантированная доставка), Channel Adapter (адаптер канала), Messaging Bridge (мост), Message Bus (шина сообщений), HTTP

## Каталог

| Паттерн | Когда |
|---|---|
| Point-to-Point Channel (канал точка-точка) | ровно один консьюмер съест сообщение (конкурирующие ок — победит один) |
| Publish-Subscribe Channel (канал публикация-подписка) | все текущие подписчики получают копию |
| Datatype Channel (канал типа данных) | на канале один тип/формат сообщений |
| Invalid Message Channel (канал неверных сообщений) | «дошло, но разобрать нельзя» — не то же самое, что dead letter |
| Dead Letter Channel (канал недоставленных) | брокер не смог доставить (истёк TTL, нет маршрута, квота) |
| Guaranteed Delivery (гарантированная доставка) | persist на диске, пока не доставят; цена — I/O и «застрявшие» |
| Channel Adapter (адаптер канала) | приложение без messaging-API сажают на канал |
| Messaging Bridge (мост обмена сообщениями) | два разных брокера, сообщения перетекают |
| Message Bus (шина сообщений) | общая инфраструктура + каноника, новые системы подключаются без переделки всех |

## Point-to-Point vs Publish-Subscribe (точка-точка vs публикация-подписка)

PTP: задача / команда / документ «обработай это один раз». Несколько Competing Consumers (конкурирующих потребителей) — нагрузка и failover (отказ на запасной).

Pub/Sub: событие «случилось». В JMS это Topic (топик). В MSMQ на момент книги нормального topic нет (см. гл. 6). TIBCO subject — дешёвые виртуальные каналы.

## Datatype Channel (канал типа данных)

Смешивать заказы и инвентарь на одном канале = каждый консьюмер пишет свой фильтр и ошибается. Лучше канал на тип. Если типов взрыв — Canonical Data Model (каноническая модель данных) + роутер, не бесконечные каналы.

## Invalid vs Dead Letter (неверное vs недоставленное)

- Invalid (неверное): получатель понял, что это не его контракт (не тот тип, схема, бизнес-поля). Это решение приложения.
- Dead Letter (недоставленное): инфраструктура сдалась. Часто expired market data (протухшие рыночные данные), как в гл. 13.

Не класть бизнес-ошибки в DLQ «потому что очередь так называется».

## Guaranteed Delivery (гарантированная доставка)

Store-and-forward (сохранить-и-переслать). Нужна, когда потеря сообщения дороже диска. Не нужна для котировок, которые через 50 мс всё равно устареют (тогда Message Expiration / срок жизни + можно потерять).

## Channel Adapter и Bridge (адаптер и мост)

Adapter (адаптер): файл, JDBC, COM, HTTP → канал (и обратно). Сам адаптер — Message Endpoint (конечная точка).

Bridge (мост): пара адаптеров между двумя MOM (TIB↔MQ в гл. 13). Иногда с CORBA/JNI, если ещё и языки разные. Message Translator (транслятор) связан, но translator меняет формат; bridge меняет транспорт.

## Message Bus (шина сообщений)

Не продукт, а стиль: каналы + каноническая модель + адаптеры. Новое приложение подписывается, старые не переписывают point-to-point паутину. SOA/service bus — родственник. Шина без дисциплины форматов — просто общий брокер.

## Связанные паттерны

Message (сообщение), Message Endpoint (конечная точка), Message Expiration (срок жизни), Competing Consumers (конкурирующие потребители), Canonical Data Model (каноническая модель), Message Translator (транслятор), Message Router (маршрутизатор)
