- **Якоря:** Widget-Gadget, integration (интеграция), loosely coupled (слабо связанный), Message Channel (канал сообщений), Canonical Data Model (каноническая модель данных)

## Зачем интегрировать

В энтерпрайзе сотни приложений: своё, пакеты, легаси. Даже SAP/Oracle/PeopleSoft закрывают кусок функций — ERP сам главный point of integration (точка интеграции). Best-of-breed (лучшее в своём классе) даёт гибкость и размазывает границы (биллинг лезет в CRM и наоборот). Пользователю всё равно: «сменить адрес и проверить платёж» режет customer care + billing. Place order (разместить заказ) легко трогает 5–6 систем. Нужен надёжный обмен данными между ними.

## Что реально сложно (не «поставим EAI-сюиту»)

1. Политика / Conway (Конвей): после интеграции отдел больше не владеет «своим» приложением
2. Сбой потока = миллионы в потерянных заказах
3. Endpoint (конечная точка) часто нельзя менять — интеграция закрывает дыры снаружи
4. «Стандарты» фрагментируются (XML ≠ общая семантика «account» / счёт)
5. Эксплуатация тяжелее разработки: мониторинг, скиллы размазаны

Интеграция не делает IT проще. Паттерны — как думают те, у кого получается: именованные решения, общий язык, не серебряная пуля.

## Карта «wide world» (широкий мир)

- **Information portals** (информационные порталы) — собрать UI из многих систем
- **Data replication** (репликация данных) — копии данных
- **Shared business functions / SOA / service bus** (общие бизнес-функции / SOA / сервисная шина) — вызвать чужую функцию
- **Distributed business process** (распределённый бизнес-процесс) — координатор поверх уже существующих систем
- **B2B** — те же силы + интернет, безопасность, чужие форматы

Граница SOA и process-движка (процессного движка) размыта: сервисы снаружи, процесс внутри одного приложения.

## Loose coupling (слабая связанность)

Меньше допущений между сторонами = хуже эффективность, лучше переживание сбоев и замен.

Локальный вызов — максимум допущений (процесс, язык, число параметров, синхронность, нет сети). RPC/RMI/CORBA/DCOM/.NET Remoting/RPC-SOAP пытаются это сохранить на сети и врут: сеть медленная, падает, другая платформа, неясно сколько ждать. Waldo 1994.

Messaging (обмен сообщениями) режет допущения: очередь, данные, асинхронность. Цена — сложнее модель программирования.

## 1 minute EAI (EAI за минуту)

Типичный маркетинговый рисунок: шина посередине, адаптеры к пакетам. Правда: адаптер, трансформации, маршрутизация, исключения, управление — это и есть книга.

## Пример Widget-Gadget Corp

Слияние Widget и Gadget. Нужно принять заказ, проверить кредит/склад, посчитать, отгрузить, выставить счёт — системы разные, менять их почти нельзя.

Черновик решения языком паттернов (превью, детали в гл. 3–11):

1. Channel Adapter (адаптер канала) — втащить приложение на шину
2. Messaging Bridge (мост обмена сообщениями) — если две разные MOM
3. Canonical Data Model (каноническая модель данных) + Message Translator (транслятор сообщений) — не учить каждую систему формату каждой
4. Pipes and Filters (трубы и фильтры) — шаги обработки как отдельные фильтры
5. Content-Based Router (маршрутизатор по содержимому) — куда заказ
6. Content Enricher (обогатитель содержимого) — добрать кредит/склад, которых нет во входящем сообщении
7. Scatter-Gather (разброс-сбор) / Recipient List (список получателей) + Aggregator (агрегатор) — опросить несколько складов/поставщиков
8. Process Manager (менеджер процесса) — долгий процесс заказа не впихнуть в один фильтр
9. Invalid Message (неверное сообщение) / Dead Letter Channel (канал недоставленных) — мусор и недоставленное
10. Control Bus (шина управления) / Wire Tap (прослушка) — потом смотреть, что происходит

К концу главы читатель узнаёт имена. Реализации — дальше.
