# Глава 13. Integration Patterns in Practice (Паттерны интеграции на практике)

- **PDF:** стр. 528–547
- **Автор кейса:** Jonathan Simon
- **Это не каталог паттернов.** Реальный bond trading desk (торговый стол облигаций), 2 года от дизайна до продакшена. Выбор паттерна под силы: бизнес, легаси, вендор, клиент.
- **Якоря:** Messaging Bridge (мост), Channel Adapter (адаптер канала), Publish-Subscribe (публикация-подписка), Point-to-Point (точка-точка), Aggregator (агрегатор), Message Dispatcher (диспетчер), Observer (наблюдатель), TIBCO, MQSeries, Competing Consumers (конкурирующие)

## Задача системы

Трейдеры прайсят много облигаций в несколько trading venues (торговых площадок), у каждого свой UI. Нужен один толстый клиент: аналитика + отправка цен.

Поток:

1. Market data (рыночные данные; цены buy/sell) приходит в систему
2. Analytics Engine (движок аналитики) считает трейдер-специфичные функции
3. Изменённые цены уходят в venues, где другие фирмы торгуют

## Что уже есть (легаси)

- Клиент: Java thick client (толстый клиент; Windows NT + Solaris, нужен быстрый UI)
- Market Data Price Feed (C++): публикует на TIBCO TIB
- Analytics Engine (C++): считает, снова в TIB
- Contribution Server (C++): говорит с venues (чужие системы)

Прямой клиент → легаси серверы = слишком много бизнес-логики на десктопе. Ставят два Java-gateway (шлюза):

- Pricing Gateway — market data
- Contribution Gateway — отправка в venues

## Стиль интеграции: клиент ↔ gateway

Четыре стиля гл. 2:

| Стиль | Вердикт |
|---|---|
| Shared Database (общая БД) | нет: не тащить SQL на клиент |
| File Transfer (передача файлов) | нет: латентность убивает цены |
| RPC (RMI/CORBA/EJB) | клиент→сервер ещё терпимо; сервер→N клиентов — ад |
| Messaging (обмен сообщениями) | да |

Почему RPC ломается на публикации цен: gateway должен помнить всех живых клиентов, кто какие бумаги хочет, и на каждый тик (много раз в секунду) звать каждого в своём потоке.

Messaging: канал на тип данных, gateway кладёт сообщение, кто подписан — получает. Gateway не знает, сколько слушателей.

Клиент→gateway тоже можно RPC (два сервера, синхронно ок), но раз messaging уже есть — всё через него. JMS → Message Bus (шина сообщений) для будущих приложений банка.

Брокер: IBM MQSeries JMS («IBM shop», WebSphere, site license).

## Мост TIB ↔ MQSeries

Нужно, чтобы JMS-консьюмеры видели TIB-сообщения.

- Message Translator (транслятор) через C++ MQ-клиент — жертвует независимостью от JMS-сервера
- Java API TIBCO клиентский архитектор отверг
- CORBA + JNI: CORBA — стандарт компании

Решение: Messaging Bridge (мост) = пара Channel Adapter (адаптеров канала; C++/TIB и Java/JMS) + CORBA между ними. Адаптеры сами — Message Endpoint (конечная точка). Один паттерн собирают из других; контекст Channel Adapter сдвинут: не «messaging ↔ не-messaging», а «две шины + другой язык».

## Структура каналов market data

TIB: один Publish-Subscribe Channel (канал публикация-подписка) на облигацию. Каналы дешёвые — это subject/topic в одном потоке, не отдельные очереди. ~100k каналов на фиде нормально.

Фильтр на подписчике (Message Filter / фильтр сообщений / Selective Consumer / избирательный) vs подписка только на нужные subject: здесь фильтрация уже в TIB, свои фильтры не пишут.

Analytics нельзя переиздавать в тот же bond-канал: аналитика трейдер-специфичная, затрёт рыночные цены. Два варианта:

1. Один канал на трейдера
2. Один канал на пару трейдер+облигация

Берут (2). Каналов много (верх ~20 трейдеров × пара сотен бумаг < 10k — меньше, чем фид). Система почти статическая, каналы умеют автозаводиться.

Почему не (1): тогда Analytics Engine становится Content-Based Router (маршрутизатором по содержимому) под это приложение. Движок — общий сервис Message Bus, его не засоряют.

До клиента тысячи каналов не тащат. Content-Based Router кладут в Pricing Gateway, не в C++ адаптер (не рвать логику C++/Java, не терять фильтрацию TIB). Gateway подписывается на все нужные TIB-subject и на JMS отдаёт мало каналов: порядка одного на трейдера.

## Какой JMS-канал

Два типа: Point-to-Point (Queue / очередь) и Publish-Subscribe (Topic / топик).

Бизнес: трейдер может сидеть на нескольких машинах сразу.

- Broadcast всем клиентам + фильтр на GUI — нельзя: слишком много тиков, жрёт CPU зря
- PTP на инстанс клиента — нельзя: апдейт цены получит только один десктоп
- Recipient List (список получателей) по инстансам трейдера — работает, дорого в коде
- Pub/Sub на канал трейдера — все его десктопы получают

Обратная сторона pub/sub: два инстанса сервера оба съедят одно сообщение → неверные цены.

Поэтому каналы односторонние:

- сервер → клиент: Publish-Subscribe (публикация-подписка)
- клиент → сервер: Point-to-Point (точка-точка)

## Починка в рантайме

### Мигание ячеек (GUI замерзает)

Несколько апдейтов в секунду, иногда < 1 мс между ними. GUI-поток захлёбывается.

Message Filter «выкинуть всё ближе 5 мс» — нельзя: у бумаги ~50 полей, соседние сообщения обновляют разные поля, потеряешь данные.

Aggregator (агрегатор): копит поля одной бумаги, схлопывает. Выгодно, только если много апдейтов одной бумаги (в их трафике так и есть: 1000 сообщений → 4 бумаги = 4 исходящих; 1000 → 750 бумаг = почти без выигрыша).

Completion algorithm (алгоритм завершения) паттерна не подходит: агрегатор не должен решать, когда слать — узкое место клиент. Клиент делают Polling Consumer (опрашивающий потребитель): фоновый цикл по бумагам. Клиент шлёт Command Message (команду) «дай апдейт», агрегатор отвечает Document Message (документом) с изменёнными полями.

### Прод упал

MQSeries лёг. Dead Letter Channel (канал недоставленных; dead letter queue) раздулась expired market data (протухшими рыночными данными; Message Expiration / срок жизни) от slow consumer (медленного потребителя). Тики тухнут в канале, пока GUI не успевает.

Aggregator сюда нельзя: цены в venues надо форвардить сразу, копить нельзя.

Competing Consumers на pub/sub не работают: все получат одно и то же.

Message Dispatcher (диспетчер): один слушатель сразу отдаёт Performer из пула и возвращается на канал. Параллель как у Competing Consumers, но на Topic тоже ок. Сообщения больше не истекают в брокере; устаревшие цены — уже проблема клиента, не очереди.

Паттерны не закрыли корень: клиент — бутылка. Потом переложили поток: Pricing Gateway → Contribution Gateway напрямую, минуя GUI. Паттерн чинит дизайн, не заменяет его.
