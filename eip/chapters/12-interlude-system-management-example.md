# Глава 12. Interlude: System Management Example (Интерлюдия: пример управления системой)

- **PDF:** стр. 503–527 (`EIP Enterprise Integration Patterns.pdf`)
- **Пререквизиты:** гл. 9 (Loan Broker / кредитный брокер, MSMQ/C#), гл. 11 (паттерны System Management)
- **Это не новая глава паттернов.** Это пример: тот же Loan Broker обвешивается мониторингом снаружи.
- **Якоря:** Control Bus (шина управления), Smart Proxy (умный прокси), Test Message (тестовое сообщение), Message Router (маршрутизатор), Message Translator (транслятор), Competing Consumers (конкурирующие), Idempotent Receiver (идемпотентный получатель), Mediator (посредник), failover (отказ на запасной), Return Address (адрес возврата)

## Задача

Показать, как паттерны гл. 11 работают на живом потоке, если компоненты — чёрные ящики: нет доступа к внутренностям, только каналы.

## Поток, который инструментируют

1. Test Client (тестовый клиент) шлёт запрос котировки
2. Loan Broker — Process Manager (менеджер процесса): кредит + банки
3. Credit Bureau (бюро кредитов) считает credit score
4. Banks отдают ставки

Клиент в проде метрики за нас не собирает. Внешний Credit Bureau может молчать или врать. Нужна консоль, QoS, проверка сервиса, failover.

## Требование → паттерн

| Требование | Паттерн | Зачем |
|---|---|---|
| Одна консоль на все компоненты | Control Bus (шина управления) | Отдельные очереди только для управления, не для заявок |
| Время ответа брокера и глубина очереди | Smart Proxy (умный прокси) | Клиент сам задаёт Return Address — без прокси reply некуда слушать |
| Жив ли Credit Bureau | Test Message (тестовое сообщение) | Периодический запрос со своим reply-каналом |
| Падение бюро → запасной провайдер | Message Router (context-based / по контексту) + Message Translator (транслятор) | Роутер слушает консоль, не монитор |

Консоль — Mediator (посредник; GoF): монитор не дёргает роутер напрямую. Правила failover живут в одном месте.

## 1. Management Console + Control Bus (консоль управления + шина управления)

Консоль получает метрики и статусы, шлёт команды (переключить маршрут, сменить параметр).

- Шина управления отделена от бизнес-каналов
- UI в книге нарочно примитивный: цель — механика, не дашборд
- JMX/WMI не используют: меньше привязки к вендору, видны внутренности решения

## 2. QoS Loan Broker через Smart Proxy

Проблема: клиент указывает Return Address (адрес возврата), фиксированного reply-канала нет.

Как вставляют прокси (прозрачно для клиента):

1. Прокси слушает старый вход брокера: `loanrequestQueue`
2. Брокер стартует на новом входе: `brokerRequestQueue`
3. Брокер отвечает на фиксированный `brokerReplyQueue`
4. Прокси кладёт reply на исходный Return Address клиента

Что меряет:

- Время request → reply
- Сколько запросов ещё не отвечено (очередь + обработка; различить нельзя)

Что шлёт на Control Bus:

- Не каждое сообщение (прокси и так удваивает трафик)
- Сводку по таймеру (~5 сек): min / avg / max времени и размера очереди
- Считать сводку в момент отправки, не на лету: так проще менять детализацию

Наблюдение из прогона (2 клиента × 50 запросов): брокер не падает при всплеске (~90 pending), но ответ растягивается почти до минуты. Узкое место раньше уже было Credit Bureau. Лечение: несколько инстансов брокера или бюро.

## 3. Проверка Credit Bureau: Test Message

Бюро поддерживает Return Address → тестовый запрос не ломает боевой поток: свой reply-канал, отдельный Test Message Separator (разделитель тестовых сообщений) не нужен.

Состав монитора:

- Test Data Generator (генератор тестовых данных) — фиксированный SSN «фиктивного» человека
- Test Data Verifier (верификатор) — не конкретные цифры (в примере бюро отдаёт random), а диапазон (score 300–900, history 1–24), тип тела, Correlation Identifier (идентификатор корреляции)
- Два таймера: Send (интервал между тестами, порядка минуты) и Timeout (секунды). После ответа или таймаута Send запускается заново

Что уходит на шину:

- Ошибка, плохие данные, таймаут
- «OK» только если до этого было плохо и снова заработало
- На старте — announce (объявление), чтобы консоль увидела монитор

Приоритет тестовых сообщений выше обычных, чтобы очередь заявок не маскировала отказ сервиса. Объём тестов маленький: иначе тесты сами задавят боевой поток.

## 4. Failover Credit Bureau (отказ на запасное бюро)

Competing Consumers (конкурирующие) на одной Point-to-Point (точка-точка) очереди уже дают простой failover и load balancing (балансировку нагрузки). Здесь этого мало:

- Внешний сервис может быть SOAP/HTTP без competing consumers
- Нельзя сплитовать трафик: квоты, дешёвый primary / дорогой backup

Схема:

1. В канал запросов к бюро встаёт Context-Based Router (маршрутизатор по контексту)
2. `control = 0` → primary, `control = 1` → secondary
3. У secondary другой формат → пара Message Translator (трансляторов)
4. Монитор продолжает бить primary, пока тот мёртв
5. Когда primary ожил — консоль возвращает роутер на него

Команда роутеру приходит отдельным Control Receiver (получатель управления) с Control Bus. Монитор secondary в диаграмме не показан, но ставится тем же классом.

## Консоль: события внутри приложения

Внешне Control Bus — Point-to-Point, значит один consumer. Внутри консоли его размножают делегатами ≈ внутренний Publish-Subscribe (публикация-подписка):

1. Сообщение с шины
2. Logger пишет файл
3. MonitorStatusHandler читает XML слабосвязанно (поля, не жёсткий тип) — консоль живёт, если в сообщение добавят поле
4. UI-контролы фильтруют по ID компонента и меняют цвет
5. FailOverHandler при смене OK ↔ не-OK шлёт `0`/`1` на command-канал роутера и обновляет картинку маршрута

Визуализация потока:

- Static analysis (статический анализ): кто публикует и кто подписан на канал (репозиторий EAI сильно помогает)
- Dynamic analysis (динамический анализ): смотреть живые сообщения; проще с Message History (историей сообщения) или полем «отправитель»

Вендорские GUI (в книге — Fiorano Tifosi и аналоги) рисуют тот же Control Bus из коробки. В примере связи захардкожены.

## Ограничения примера

- Сообщения, уже стоящие у упавшего primary, там и остаются. Брокер по Correlation Identifier жив, но эти заявки ждут, пока primary не встанет
- Чтобы не ждать: re-send (повторная отправка) из брокера или буфер в роутере с повторной отправкой. Будут дубликаты — нормально, если Credit Bureau и Loan Broker — Idempotent Receiver (идемпотентный получатель)
- Показан узкий срез management. Heartbeat (пульс), пороги по всему графу, трафик на каждом хопе — не сделаны
- Вывод главы: обвязка управления часто стоит столько же, сколько сам messaging-поток, или дороже
