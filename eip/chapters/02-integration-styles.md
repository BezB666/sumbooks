# Глава 2. Integration Styles (Стили интеграции)

- **PDF:** стр. 63–74
- **Роль:** четыре способа склеить приложения. Messaging (обмен сообщениями) — один из них, не религия.
- **Якоря:** File Transfer (передача файлов), Shared Database (общая БД), Remote Procedure Invocation (удалённый вызов процедуры), RPC, Messaging (обмен сообщениями)

## Критерии выбора

- Связанность: минимум допущений, чтобы системы эволюционировали порознь
- Простота: меньше правок в приложениях и меньше интеграционного кода (часто конфликт)
- Технология: спецсофт, lock-in (зависимость от вендора), порог входа
- Формат данных и как он будет меняться
- Свежесть данных: лучше часто и маленькими кусками
- Данные или поведение (вызвать функцию, не только отдать запись)
- Асинхронность: удалённая сторона может спать / сеть лежит

Одна система может использовать разные стили на разных стыках.

## Четыре стиля

| Стиль | Как | Сильно | Слабо |
|---|---|---|---|
| File Transfer (передача файлов) | пишу файл, другой читает | просто, есть везде, развязка по времени | латентность, кто удаляет файл, формат, нет вызова поведения |
| Shared Database (общая БД) | общая схема, одна физическая БД | нет копий, сразу видно всем | связанность схемой, бои за модель, нагрузка, не вызывает поведение |
| Remote Procedure Invocation (удалённый вызов) | экспорт процедур, синхронный вызов | знакомый RPC, данные+поведение | сеть как локальный вызов (ложь), доступность, версионирование API |
| Messaging (обмен сообщениями) | общая шина, пакеты в каналах | асинхронность, буфер, надёжность, много-ко-многим | сложнее модель, инфраструктура, отладка |

### File Transfer (передача файлов)

Договор: имя, путь, формат, когда писать/читать, кто чистит. Пакетные интеграции, EDI-корни. Часто Combined with (совмещено с) ночной batch (пакетной обработкой).

### Shared Database (общая БД)

Одна правда. Цена: все приложения обязаны жить в одной модели. Интеграция через чужой foreign key (внешний ключ). Транзакции конкурируют.

### Remote Procedure Invocation (удалённый вызов процедуры)

CORBA, DCOM, Java RMI, EJB, RPC-SOAP. Хорошо, когда нужен ответ сейчас и обе стороны живы. Плохо как универсальный клей энтерпрайза.

### Messaging (обмен сообщениями)

Канал как договор вместо файла или метода. Можно и данные, и Command Message (сообщение-команда). Получатель сам троттлит. Книга дальше только про этот стиль — не потому что остальные мёртвые, а потому что у messaging свой язык паттернов.

## Когда что

- Нет реалтайма, уже есть файлы → File Transfer (передача файлов)
- Одна доменная модель, один DBA, OLTP делят → Shared Database (общая БД; редко выживает)
- Нужен синхронный «сделай это и скажи результат» → RPC точечно
- Разные платформы, пики нагрузки, недоступность, pub/sub (публикация-подписка) → Messaging

## Связанные паттерны

Messaging (как стиль), дальше гл. 3: Message Channel (канал сообщений), Message (сообщение), Message Endpoint (конечная точка)
