# Глава 1. Layering

- **PDF:** 42–49 (печать 17–24)
- **Якоря:** presentation, domain, data source, layer vs tier, Hexagonal Architecture, complexity boosters

Слой ест сервисы нижнего и прячет его от верхнего: кусок можно понять отдельно, подменить, меньше зависимостей. Минусы — каскад «поле в UI и в БД» через все слои и лишние преобразования. История: batch без слоёв → client-server (логика в экранах или stored procedures) → три слоя, когда Web нельзя вытаскивать из fat-клиента. Layer ≠ tier: три логических слоя живут и на одном ноутбуке.

Три слоя: presentation (экран/HTTP/batch как «пользователь»), domain (расчёты, валидация, что дернуть у источника), data source (БД, очереди, чужие пакеты). Домен и источник не зовут presentation. Тест утечки: другой UI или XML вместо SQL — что пришлось копировать? Hexagonal Architecture симметричен («ядро и порты»); Fowler оставляет асимметрию: presentation — сервис, который ты даёшь; data source — которым ты пользуешься.

Источник почти всегда на сервере. HTML-presentation — тоже; rich client — на клиенте. Домен лучше весь на сервере; на клиент — изолированный кусок под отзывчивость/офлайн. Слои узла — один процесс; резать процессы без нужды = Remote Facade + DTO. Coldewey: distribution, явный multithreading, object/relational, мультиплатформа, >100 tps — «усилители сложности».
